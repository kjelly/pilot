# Quality gate: classifications and safety

| Signal | Decision | Why |
|---|---|---|
| Independent reviewer finds P0/P1/P2 (a repeated disputed claim only with new evidence), failing unit/regression tests, GH checks `fail` or `cancel` not confirmed unrelated, unresolved review threads, merge conflict | DRAFT | Confirmed defect or blocker; comment with proof and next fix |
| A secret in any commit of `baseRefOid..headRefOid` (the local scan: `--worktree`, optional `--secret-file`), even when HEAD no longer has it | DRAFT | A leaked secret, no override. The comment tells Root to stop and leaves the credential and the history to the user; a scrubbing commit does not clear it. Class, file and commit only, never the value |
| The secret scan could not run: no `--worktree`, a PR commit that is not in the clone (fetch it), a scanner that does not load, an unusable `--secret-file` | WAITING | An unscanned PR is never merged; nothing is inferred from the scan's absence |
| Live base tip is not an ancestor of PR HEAD and GitHub's test merge conflicts, or a file changed on both sides since the merge base, confirmed with fresh PR/ref reads | DRAFT | The merge train cannot integrate it: record HEAD/Base/live-base SHAs, comment then convert; `pr-ready` must merge the latest base, rerun affected checks/CI and obtain fresh independent review |
| Live base tip is not an ancestor of PR HEAD, the test merge is clean and no file changed on both sides; or only PR `baseRefOid` lags the live tip | (no effect) | The merge train integrates it before merging (`references/merge-train.md`); the rest of the gate decides |
| HEAD lacks the live tip and GitHub has not computed mergeability, or a side changed more files than the compare API lists | WAITING | Alignment cannot be classified yet |
| GH checks `pending`, review `REVIEW_REQUIRED`, PR mergeability `UNKNOWN`, unavailable GraphQL threads, stale review head/base without confirmed live-base mismatch, incomplete reviewer coverage, PR dependency not satisfied | WAITING | Transient or unverified conditions; keep Ready |
| `CHANGES_REQUESTED`; a `fail`/`cancel` check listed in `unrelated_failing_checks`; a disputed finding repeated without `new_evidence` | WAITING | The PR has nothing left to change: a reviewer has to re-review, a check has to be rerun after its cause is fixed, or a person decides between two reviews. A Draft would be undone by `pr-ready` |
| Active rules include `merge_queue` | WAITING | `gh pr merge` may enqueue or enable auto-merge without a final merge; do not trigger automatically |
| Empty CI, no documented rationale or no positive test evidence | WAITING | Absent checks are not an implicit pass |
| Every gate clear, no unresolved threads, base/HEAD unchanged, branch mergeability `MERGEABLE`, merge state `CLEAN`, tests/CI passed | MERGE | The actor queues the PR (`merge-queue` label, saved evidence); the merge train integrates the base if needed, waits for CI, reruns this gate and runs `gh pr merge --merge --match-head-commit SHA`, then verifies `MERGED` |
| The base branch's `.github/pr-evidence.json` requires a record and `target_validation` is missing, malformed, `blocked`, `not-needed` for a `required_paths` change, or `required` without a committed `docs/evidence` record that names a tested revision covering HEAD (same SHA or evidence-only delta); the manifest cannot be read | WAITING | Checked by the gate against GitHub at the base/HEAD SHAs; the gate has no finding of its own, so it never merges and never drafts |
| The reviewer's blocking `P1` at the changed path for a missing mandated actual-run record (AGENTS.md §1) | DRAFT | Hard repository rule violated; the finding names the missing `docs/evidence` record |
| Closed, already merged or Draft | SKIP | Out of scope |

Additional rules:
- A WAITING result carries `wait_kind`: `transient` (pending checks, a PR or base that moved during the gate, mergeability or merge state GitHub has not computed, any API failure, a secret scan that could not run) or `person` (everything else, including every reason nobody classified). The merge train keeps a transient PR enqueued and stops its run; it dequeues a `person` PR with the reasons so the PRs behind it can merge (`references/merge-train.md`). Nothing else about WAITING changes: the PR stays Ready.
- A review taken at an earlier HEAD covers the current one by an evidence-only delta or a pure base import only if HEAD also carries every change the base made since the fork (`base change not carried into HEAD: <path>` otherwise): a merge that keeps the PR's side of a file main changed does not inherit the review.
- Any unexpected CLI/API response or inability to inspect **active branch rules** makes the result WAITING. If branch rules cannot be read, do not auto-merge.
- Both required checks and other displayed checks must pass; skipped checks are permitted only if GitHub treats them as non-failing and reviewer has verified all relevant test areas. An unexpected bucket is WAITING.
- Unavailable or malformed live base refs or ancestry comparisons remain WAITING. The base branch name is part of the confirmed identity: retargeting to another branch at the same SHA also invalidates it. Missing names and PR/ref movement during confirmation or the final gate require a fresh gate. The actor checks that exact name and live ref before writing and again after posting a Draft explanation. Feature HEAD differing from main is normal; HEAD need not contain main either, as long as the merge train can integrate it. The train's final gate, right before `gh pr merge`, sees HEAD containing the live tip.
- No `--admin`, `--auto`, `--delete-branch`, rebase, force push, or bypass. Respect repo's allowed merge methods; no fallback to a different method without authorization. In this repository the method is `merge` (the project default of `apply_decision.py`); GitHub deletes the head branch itself.
- Complete the shared safe checkout restore before invoking the actor. A failed restore leaves PR state unchanged. Recheck the live gate after restoration with saved PR HEAD/Base and external evidence; no checkout switching follows the state change.
- Only the actor mutates PR state. Before mutation it recomputes the gate live. `MERGE` only authorizes an **attempt**; GitHub still enforces its own rules.
- Never interpret a merge queue enqueue operation as merged. Only PR remote `state == MERGED` constitutes success.
- A reviewer result is evidence, not an unconditional approval. Prefer paths, line ranges, test evidence, and explicit scope.
- For outstanding review comments: because unresolved threads can hide substantive objections, default to Draft for any unresolved thread, including outdated threads, until triaged/resolved. For unknown thread availability, WAITING.
- If a PR includes release-sensitive changes requiring human sign-off beyond configured repository branch rules (production secrets, destructive migrations, irreversible data loss), treat it as WAITING and flag the requirement explicitly; do not extrapolate permissions from CI green alone.
