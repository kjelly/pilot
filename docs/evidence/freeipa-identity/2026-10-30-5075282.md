## Preparing the VM: an existing quirk, not part of this change

On the freshly installed server, before any roster was applied, `pilot identity
drift` failed at the probe task "List live sudo rule names". On the server,
`ipa sudorule-find --raw` with no sudo rules prints `0 Sudo Rules matched` and
exits 1, and that task has no `failed_when`. The same failure occurs on the
baseline binary. Once the roster above had created sudo rules the probe ran.
This is not changed here; a FreeIPA with no sudo rules at all still cannot be
probed.

Cases L1 to L3 are the defect the second review found: ansible expands a template in a vault key (here `ansible_connection`) into its own failure message, and the probe error used to copy that message. `5075282c` never copies ansible's text: the playbook's own gate messages, a fixed vocabulary of failure classes and a fixed "details withheld" sentence are the only things reported (the other vault keys that ansible echoes, `ansible_python_interpreter`, an ssh `ansible_host`, are covered by the real-Ansible tests, not on the VM).

Cases H3 to H5 are the defect a review found in the first version of the fix: pilot always passes `target_group` now (the flag value, else `freeipa-server`), so a vault key cannot retarget the probe. The earlier cases pass `--target-group freeipa-server` explicitly; H3 to H5 omit the flag. With the flag omitted and the vault key set to a group that does not exist, `8d965563` fails and the later candidates pass; the case with two hosts (a refusing client) is covered by the real-Ansible tests.

Cases B and C on the baseline are the defect in the issue: the vault held the
password, and the operator saw only the group-name warning, not why the probe
failed.
