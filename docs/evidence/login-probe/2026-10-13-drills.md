## 2. Drill topology

`docs/topologies/login-probe-topology.yaml` (`lp-ipa`, `lp-mon`, `lp-target`,
`lp-target-el`), applied with the same chain. Before the drills:

| Spec | Result |

Alert states were sampled every 30 s from Prometheus `/api/v1/alerts` and
Alertmanager `/api/v2/alerts` on `lp-mon`; "inhibited" is Alertmanager's own
`status.inhibitedBy`. Firing-episode counts come from Prometheus' `ALERTS`
series (a gap longer than 30 s starts a new episode). Every disruptive
injection armed a systemd timer on the target that undoes it.

Defaults in force: probe interval 60 s, `login_probe_alert_for` 3m,
`login_probe_transport_alert_for` 5m, `login_probe_alert_keep_firing_for`
5m, `login_probe_stale_seconds` 180, `host_disk_latency_for` 10m,
`host_metrics_missing_for` 3m, seed `HostDown` 10m.

### S3 — I/O pressure on AlmaLinux 9 (no PSI)

Injection: a device-mapper `delay` target (300 ms per I/O) over a 256 MiB
loop file on `lp-target-el`, written by four direct-I/O loops; the system
disk was not touched. Prometheus measured `dm-0` at 0.304 s per write and
2.76 writes/s (5 m rate), queue depth about 1.

## 3. Canary key propagation (observed, not injected)

Removing the hand-made Phase 0 setup made the apply generate a new probe
key, so the canary's key in FreeIPA changed after the targets had cached the
canary. Each target served the old key until SSSD refreshed its user entry:

| Target | Last `auth` attempt | First `ok` | What preceded it |
|---|---|---|---|
| lp-mon | 07:10:37 | 07:11:37 | not identified |
| lp-target | 07:11:37 | 07:12:37 | `sssctl user-checks -a acct -s sshd pilot-login-canary` at 07:11:40 (a PAM account check refreshes the entry) |
| lp-target-el | 07:32:24 | 07:33:24 | nothing: first lookup after half of `entry_cache_timeout` (entry cached 06:46:11), consistent with SSSD's default `entry_cache_nowait_percentage=50` |

No `sss_cache` was run. While `lp-target-el` served the old key,
`PilotLoginProbeAuthFailed{lp-target-el}` fired as designed (one episode,
07:16:00–07:38:45 by `ALERTS`; the stage was `ok` again from 07:33:24 and the
alert cleared after `keep_firing_for`).
