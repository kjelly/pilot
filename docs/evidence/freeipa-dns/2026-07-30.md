## Real bugs found and fixed

All four were found by running the previously fake-shim-only-tested `playbooks/apply/
freeipa-dns-apply.yml` against a genuinely live FreeIPA server for the first time. Full
before/after diffs are in the playbook's own inline comments; summary:

1. **Leading-whitespace regex mismatch (highest severity).** Every attribute line in real
   `ipa dnszone-find`/`dnsrecord-find`/`dnsrecord-show --all --raw` output carries a 2-space
   indent (confirmed via `cat -A`: `"  arecord: 192.168.122.3$"`). Every regex in the playbook
   anchored on a bare `^attrname:` never matched. Consequence: the authoritative-mode
   stale-record-prune block-splitting (anchored on `idnsname:` lines) never actually split
   anything — the feature was completely inert, not merely unconfirmed — and
   current-value/TTL diffing always read an empty current state, which only *looked* correct in
   the one scenario tested before this round (first-time record creation, where "current is
   empty" happens to be the right answer for the wrong reason). Fixed: every such regex is now
   `^[ \t]*attrname:`.
2. **`ipa dnszone-add`'s `changed_when` never matches.** Real success output contains no
   `"Added DNS zone"` string. Fixed: `changed_when: true` (the `when:` clause already gates the
   loop to zones confirmed absent).
3. **Split-horizon self-conflict.** The `dig SOA <zone>` check queried this host's own system
   resolver; after `--setup-dns`, that resolver is the box itself, so every rerun after the first
   successful zone creation falsely detected an "upstream conflict" with the zone it had just
   created — failing the whole apply, independent of `acknowledge_split_horizon`. Fixed: the
   check now skips zones already confirmed present via the bulk `ipa dnszone-find` discovery,
   matching the spec's own stated intent ("upstream exists **and** FreeIPA doesn't yet manage
   it").
4. **(Defensive, not a functional bug) `failed_when` gap.** `Reconcile A/AAAA/CNAME record value
   and TTL` had no tolerance for FreeIPA's `"no modifications to be performed"` error, unlike the
   identical pattern already used in `freeipa-identity-apply.yml`. Added for symmetry/robustness.
5. **(Cosmetic) false CREATE_ZONE/DELETE_ZONE reports.** The `Report zone creation`/`Report zone
   deletion` debug tasks printed their message for every zone in the manifest, including ones the
   parent task skipped (already existed / not marked absent). Fixed with
   `when: not (item.skipped | default(false))`.

A fifth, independent bug was found later reconciling `freeipa-dns` through the real `pilot
reconcile` wizard as part of the round-18 minimal-poc rebuild (`ipa_server_fqdn_expected`'s
default didn't match `freeipa-server-apply.yml`'s own FQDN default) — see
`docs/verification/freeipa-dns.md` v1.1 and the round-18 evidence record for that one.

## Real scenarios validated (2-VM ad hoc environment)

Every scenario below was run against the live server, not a fake CLI shim, with a `changed=0
failed=0` clean rerun confirmed after each:

| Scenario | Real result |
|---|---|
| Zone create (merge mode) + 3 A records via `target.inventory_host: nexus` | `CREATE_ZONE`, 3x `ADD_VALUE`; `dig +short <name>.svc.pilot.internal. A @127.0.0.1` for all 3 resolved to nexus's real IP |
| Drift correction: manually injected a second `arecord` value via `ipa dnsrecord-mod`, reran the same manifest | `SET_VALUE grafana.svc.pilot.internal. A ttl=300`, `changed=1`; `dnsrecord-show` confirmed only the declared value remained afterward |
| AAAA record (explicit `values:`), CNAME record, custom TTL (120, overriding the 300 default) | All three added in one apply; `ldapsearch`/`dig` confirmed exact values |
| Explicit RRset deletion (`state: absent`) | `DELETE_RRSET`; `ldapsearch` confirmed the record no longer exists (`No such object` / attribute absent) |
| Authoritative-mode stale-record prune: manually created an unmanaged A record in a fresh `records_mode: authoritative` zone, declared a *different* record in the manifest | Same apply: `PRUNE_RRSET stale-fixture...` **and** `ADD_VALUE app-fixture...`; `ldapsearch` confirmed the unmanaged record gone (`No such object (32)`) and the declared one present |
| Merge-mode preserves unmanaged records (core guarantee, tested against a *different* zone in merge mode with the same kind of manually-added unmanaged record) | Rerun `changed=0`; unmanaged record still present afterward |
| Split-horizon gate, positive path: brand-new zone with `acknowledge_split_horizon: true` | `CREATE_ZONE`, `changed=1` |
| Zone deletion: `allow_zone_delete: true` + `-e confirm_dns_zone_delete=true` on a throwaway zone | `DELETE_ZONE`, `changed=1`; rerun `changed=0` |
| Final idempotency: rerun of the canonical 3-zone/6-record fixture manifest with zero changes | `changed=0 failed=0` |
