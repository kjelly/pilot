# pilot-access-target-policy: nothing after the reload in the block that puts the drop-in back — candidate `4aa0dab` (2026-10-13)

Scope: the PR #50 review's blocking finding, and the same shape elsewhere.

The finding: `pilot-access-target-policy-apply.yml`'s absent path removed its pre-change snapshot as the last step of the block whose rescue puts the policy drop-in back. When that removal failed after sshd had reloaded without the policy:
- the rescue wrote the drop-in back to disk and did not reload;
- sshd ran without the policy while the files said it was there, and its next restart would load it again;
- the message said "The policy drop-in is back in place and sshd was not reloaded".

The change (`4aa0dab`, on `42c5bf5` = PR #50's `41aaaf1` merged with `main` `db10268`):
- **absent:** the snapshot removal runs after the block. If it fails, the drop-in stays removed, as sshd runs it, and the snapshot stays. The run fails saying the policy was removed and sshd reloaded; the next run removes the snapshot.
- **present:** the post-reload `sshd -t` had the same shape. Its rescue puts the old drop-in back and reloads only if `sshd -t` passes again. It now runs after the block, still before the host joins `pilot-transport-ready`.
- **Search:** every block in `playbooks/apply` and `playbooks/decommission` whose rescue puts sshd configuration back:
  - gateway and Directory ForceCommand, install and removal;
  - freeipa-client's password-auth drop-in and its decommission;
  - target-policy present and absent.

  Only the two target-policy steps came after the reload.
- **New lint** `TestRegression_SshdReloadEndsItsRollbackBlock` (repo-wide): in a block whose rescue puts sshd configuration back, the reload must be the last step.
- **New localhost test** `TestRegression_SshdSnapshotCleanupFailsAfterTheReload`.

## Scenario: the snapshot removal fails after the reload

A test-only helper playbook outside the repository made the fault and took the observations. On `p50-ub` it recorded:
- the drop-in and the snapshot (present/absent, SHA-256, `lsattr`);
- `ssh.service` and its count of "Reloaded" journal lines;
- one `sshd -T` value from the files on disk.

It also observed **what the running sshd does**, not what the files say. From `p50-ipa`, the policy's gateway address, it ran `ssh -W <p50-ub>:22` (a direct-tcpip channel) to `p50-ub`:
- with the policy loaded, the daemon refuses: "channel 0: open failed: administratively prohibited";
- without it, the channel opens and returns `p50-ub`'s SSH banner.

Setup, the same for both revisions, each with its own playbooks:
- apply `present` with `remote-dev` over the installed `strict` policy. The real snapshot task saved the `strict` drop-in;
- `chattr +i` on the snapshot, so root's unlink fails.
