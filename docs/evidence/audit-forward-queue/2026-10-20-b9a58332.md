## Numbered-message and failure drills

A second fresh topology used the same candidate and actual rendered inventory.
The checked-in loopback TCP input fixture bypassed journald rate limiting for the
synthetic load. All three facilities (`local6`, `auth`, `authpriv`) had independent
sequence IDs on each client; the receiver counted unique IDs, missing IDs and
duplicates from its output files. The fixture is test-only.

| Scenario | Sent | Received unique | Missing | Duplicate copies | Exit / verdict |
|---|---:|---:|---:|---:|---|
| Receiver restart during continuous sending | 1,440 | 1,437 | **3** | 0 | **1 / FAIL zero-loss criterion** |
| Receiver confirmed stopped before sending, then recovered | 1,440 | 1,440 | **0** | 0 | 0 / PASS |
| Disk spill, clean client restart while receiver stays stopped, then receiver recovery | 72,000 | 72,000 | **0** | 2 | 0 / PASS unique-ID recovery |

In the live restart, Ubuntu lost sequence 58 in each of the three facilities;
AlmaLinux lost none. These results are consistent with TCP's unacknowledged
in-flight window; they do not establish which endpoint discarded each message.
`ResendLastMSGOnReconnect` can repeat the last message and cannot establish
durable receipt. See the [upstream omfwd documentation](https://docs.rsyslog.com/doc/configuration/modules/omfwd.html#resendlastmsgonreconnect).
The original issue's zero-loss restart criterion is therefore **not met**; the
accepted scope is queue recovery with this explicit TCP limitation.

Both action queues on both clients actually wrote spool data before the persistence
test restarted them (audit/auth about 3/9 MiB per client). The spill scenario first
confirmed the old receiver connections were disconnected, isolating queue
persistence from the live TCP window. Each action has a separate filename, a
256 MiB disk budget, save-on-clean-shutdown and unlimited retries; bounded storage
does not cover indefinitely long outages or sudden power loss.

An exploratory baseline on pre-fix `1790e2e8` under the numbered restart load
received 354/1,440 and lost 1,086 (543 per client), with no duplicates. It is a
separate baseline, not evidence for the final candidate. Timing-sensitive counts
are observations, not promised fixed counts on every restart.
