## Root cause (measured on the base, SSSD 2.9.4 and 2.9.8)

`sss_cache -E` only expires rules a client already holds. A rule that newly applies reaches the client through SSSD's smart refresh (default 15 min), full refresh (6 h) or start-up. The backend log of a restart shows `Task [SUDO Full Refresh]: scheduling task 10 seconds from now`, and `sudoLastFullRefreshTime` in `cache_<domain>.ldb` advances about 10 s after the restart (the helper reported 10.3–10.5 s in each of six runs I watched, including runs 3 s after the previous refresh; those outputs and the backend log excerpt were not kept).

| Change made on the server (by hand, `ipa` CLI, base) | `sss_cache -E` alone | restart |
|---|---|---|
| new rule | still denied | allowed |
| user added to an existing rule | still denied | allowed |
| host added to a hostgroup a rule names | still denied | allowed |
| user added to a group a rule names | allowed | allowed |
| command added to a command group | allowed | allowed |
| rule deleted, or user/group/host/command removed | denied (with no action: still **allowed**) | denied |

An offline-to-online cycle (SIGUSR1/SIGUSR2) also forced a full refresh within seconds in one hand run; it was not used or measured further.

## Failures and invalid phases (not rewritten as passes)

- **First candidate `5c020dda`, superseded.** Suspending a client during the apply made the gate itself fail with `object of type 'dict' has no attribute 'rc'` instead of naming the client: an unreachable loop item registers no `rc`. Fixed in `1aab08cb`.
- **Second candidate `1aab08cb`, superseded.** An independent review found that a client without `ldbsearch` produced a Python traceback instead of the instruction, and that the gate derived "unfinished" only from the shape of the result (a task-level failure registers no `results`). Both fixed in `311af100`, which also stopped declaring the timeout as a play var. The whole matrix above, the chain and the receipts were re-run on `311af100`.
- Earlier runs on `1aab08cb` had two void phases: the network-block step used `nft`, which AlmaLinux does not ship, and the `--tags sudo` step used a roster change outside the `sudo` tag. Both were redone (rows 8–9 and 11–12).
- **Unrelated intermittent test failure.** `make test` failed in the audit-log-forwarding Step 1d preflight (`Broken pipe` from a shell task that exits without reading the awk program it is given on `stdin`) on `1aab08cb` (`TestAuditLogForwardingStep5cFollowsASymlinkedPolicy`), on the docs-only commit after `311af100`, and twice on the PR tip (`TestAuditLogForwardingStep5ChainUnderAnsible`); it passed on `311af100` and on the commit before the squash, whose tree is identical to the PR tip apart from this record. That playbook, its tests and `cmd/pilot/cmd` are not changed by this PR. The same race reproduces with a minimal playbook containing no Pilot code (a `shell` task that exits without reading its `stdin`): 0 of 30 runs failed on an idle machine and 13 of 40 under CPU load, every one with `Broken pipe`. The two failing tests passed 8 of 8 in isolation on the untouched base, and the whole `cmd/pilot/cmd` package passed once on the base. The final unit receipt therefore ran with `-p 3` to lower CPU contention and passed.
- One `make identity-ssh-cache-test` run on the docs-only commit after `311af100` failed once in `TestRegression_IdentitySSHCacheRuntime`, in the SSH-key path this PR does not change: one loop item returned `Module result deserialization failed: No start of json char found` (non-JSON from the controller-side Python, which is a `mise` shim here) and never ran. The identical test passed 5 of 5 reruns and the receipt then passed.
- During the blackhole step, `ip route get` on the blocked address printed `RTNETLINK answers: Invalid argument`; that is the kernel's answer for a blackhole route, and SSSD's `connect failed [22]` in its backend log confirms the block took effect.
