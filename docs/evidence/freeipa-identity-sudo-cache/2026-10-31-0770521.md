### 3. Zero sudo rules; marker absent

On the freshly enrolled clients of the matrix the provider had no sudo rule and no sudo defaults (read back over LDAP: `cn=sudorules,cn=sudo` empty, no `sudoRole` object). After the client apply's restart the marker appeared 10 s later on both OSes (SSSD started 17:23:21, marker 1793467411), and the first identity apply with zero sudo rules (roster `s2`) converged at 10.3 and 10.4 s. So an identity-only roster does not make the helper time out. The "attribute absent before the restart" state could **not** be produced: after the cache database was removed with SSSD stopped and SSSD started again, the marker was present 0.02 s after `systemctl start` returned (value = the start second), and the helper then converged in 10.5 s (Ubuntu) and 10.4 s (AlmaLinux). The helper's absent-attribute branch (`None`) is therefore exercised only by the repository's fixture tests, not by a native service.

## Failures, superseded results and surprises

- **Old rule of the previous record (`311af100`, helper SHA-256 `c0e187dd…065d`, also the helper at `38f72218`).** The helper accepted `sudoLastFullRefreshTime >= int(time.time())` taken before the restart. Reproduced here: the same-second race (6/6 false convergence) and the stepped-back clock (0.2 s convergence with no refresh). The candidate requires a value that differs from the pre-restart marker and is later than the second the restart returned, and fails closed in both cases. The review finding of the stale marker on that commit ([PR comment](https://github.com/kjelly/pilot/pull/222#issuecomment-6544352155)) is reproduced and fixed on this head.
- **Chain attempt 1 (fresh hosts, L3).** The identity fixtures failed in `--check` on nodes with no FreeIPA: `Task failed: Module failed: Error executing command: [Errno 2] No such file or directory: b'kinit'` at `freeipa-identity-apply.yml:914` (`Kinit admin`; the task is not changed by this PR). The identity reconciler is a day-2 playbook and cannot preview before a server exists. The recorded chain skips the three identity fixtures in `--check` only and previews the identity playbook separately against an installed server (invariant 1). The server and client plays were previewed on the fresh nodes.
- **Chain attempts 2 and 3 (L4, harness).** The committed identity fixtures are written to be applied as separate invocations. Back to back in one run, the previous play's `set_fact` values shadow the next play's defaults: `Canonical rosters require schema_version: 1, 2, or 3 and must not mix users/groups/hostgroups/hbac/sudo with legacy ipa_* lists.` Attempt 3 reset `freeipa_roster` as well, which blocked the roster `include_vars` (`ipa_users/ipa_groups/… are all empty, so this apply would do nothing but still report success`). Attempt 4 reset only the seven list names and one flag listed above and passed. This is a property of the fixtures and the harness, not of this PR.
- **Entry-point harness.** The first `pilot reconcile` attempt stopped at `component "freeipa-server" host "…" resources cpu=2 ramMiB=3911 diskGiB=27 (available on /) are below minimum cpu=2 ramMiB=4096 diskGiB=20`, because `pilot reconcile` first applies the required dependency `freeipa-server`; the topology was rebuilt with a 4.5 GiB provider. A second attempt applied the dependency with a stale `freeipa_server_ip` that pilot had written into the workspace `group_vars/freeipa.yml` during the first attempt, which pinned the wrong address and made the server apply fail with `ipa: ERROR: [SSL: CERTIFICATE_VERIFY_FAILED] … self-signed certificate in certificate chain`; the workspace value was corrected and the arm rerun from the snapshot. Running pilot's inventory parser with `ANSIBLE_VERBOSITY` set also fails (`parse ansible-inventory output: invalid character 'U'`), so the entry-point arms ran without it.
- **F1 — the claim "user added to an existing rule needs a restart" does not hold for a cached rule.** `playbooks/apply/freeipa-identity-apply.yml` (comment above the refresh tasks, lines 3986–3989: "new rule, user added to an existing rule, host added to a hostgroup a rule names … reaches the client only through SSSD's smart/full refresh or start-up") and the row "user added to an existing rule | still denied | allowed" of the `311af100` evidence record are not reproduced: D2 and the by-hand check both show `sss_cache -E` alone delivers it when the rule is already in the client's cache. The fix itself is unaffected (D1 and D3 still need the restart). The runbook, the known-gotchas note, the spec changelog and the superseded record are corrected in the evidence commit. The playbook comment itself is deliberately left unchanged so that the tested file hash stays valid; it overstates the case (it lists "user added to an existing rule") and is a follow-up comment-only fix.
- **F2 — the restart outage is not zero for PAM/SSH/sudo and uncached users.** The previous runbook sentence (about 680 `getent`/`id` probes of a cached user: no failure; PAM/SSH logins and uncached users not tested) is true for what it measured; this run shows 1–3 failures per client around the restart (up to about 0.2 s) for SSH login, `sudo -l` and the first uncached lookup.
- **Not reproduced: marker attribute absent before the first dirty apply** (see 3).
- **Side finding, not changed by this PR: the roster admin password is printed at `-v`.** `freeipa-identity-apply.yml:255` (`Fill canonical roster freeipa.server for this reconcile`, a `set_fact` of the whole roster, no `no_log`) prints `freeipa_roster` including `freeipa.admin.password` when the roster omits `freeipa.server` (the v2 fixture does), as soon as the run is verbose (`-v`). The chain and one fixture run here used `-v`; the two raw logs were redacted in place and a scan of every raw log and of this record for each secret-looking vault value found no other occurrence. Runs without `-v` print nothing for that task.
- The `sudo -l -U <user> -- /usr/bin/id` command prints nothing and exits 1 when the user is not allowed, so the probe records its exit code next to the output.
- During the ssh-based observer, a single sample read `marker=none` for 0.1 s while SSSD wrote its cache (`ldbsearch` raced the write); the helper treats a missing marker as "not yet" and keeps polling.
