## Not covered / limits

- **Signals print nothing.** `host decommission apply` and `resume` install no signal handler. A Ctrl-C or SIGTERM during the wait ends the process at once with no message (L4, L11A). The state is unchanged, as the tables show. Review finding F2: spec and runbook wording will say so.
- **Orphaned lock-wait ssh.** A Ctrl-C while waiting leaves the lock-wait ssh queued on the server until the holder releases (L8). It then takes and drops the lock at once. Spec P3-6; the clean-up is P2-6's scope.
- **Unlocked tail after SIGKILL.** A SIGKILLed pilot leaves its ansible-playbook running for about 3 s without the lock (L7, X5).
- **Fork workers can outlive pilot.** A lost lock kills only the main ansible-playbook process (R2). One fork worker outlived pilot by under 2 s on an earlier candidate; none did in this run.
- **TUI decommission waits blocking.** The TUI decommission uses the default 30-minute wait, synchronously (review finding F1). It was not driven live.
- **Lock lost after Finalize.** The run would return `ErrLockLost` even though the receipt exists; a rerun replays the receipt (R16, review finding F3). This was not triggered live.
- **Decommission inputs.** The decommission arms need `ipa_client_fqdn` (#303) and a decrypted roster (#294). Both gaps predate this PR.
- **Pre-existing `--actions` holes.** #300 and #301 cover the other `pilot edit --actions` steps whose failures are not reported to automation, and #302 covers `delete_host`.
- **Not run live:** password-based SSH (only the `ansible_password` refusal was), real bastion hosts, and production-sized inventories. Spec U1: the maintainer confirmed on 2026-11-06 that production inventories use none of the refused forms.

## K20: what allow and deny mean on the client

Measured before the arms, with the same RPCs the Go writer sends, on the enrolled client (SSSD). Two oracles, and the arms use the one that fits what they claim:

| Oracle | What it reads | Behaviour measured |
|---|---|---|
| Login | a fresh ssh login by password and by key, then `sudo -n /usr/bin/true` inside that login | follows the server at once: allow means both succeed, deny means the login or `sudo -n` fails |
| Cache | as root on the client: `id -nG <user>` (still in the sudo role group) and `sudo -l -U <user>` (still lists the rule) | stale: it does not change by itself |

| Step | Observation |
|---|---|
| Warm (three users: one to be removed from the sudo role group, one to be disabled, one to be deleted; a second set of the same) | all of them: password and key login allow, `sudo -n` allow, cache allow |
| Revoked on the server, then 6 s later the cache of set 1 | unchanged for all three |
| 11 s after the revocation, fresh logins of set 1 | removed from the role group: ssh allow, `sudo -n` deny; disabled: ssh deny (password and key); deleted: ssh deny |
| Set 2, cache only, a bounded wait of 300 s (19 polls, no refresh) | never changed by itself |
| Set 2 after `sss_cache -E` and an sssd restart | removed user: cache deny within 2 s; deleted user: `id` no longer resolves within 2 s; **the disabled user's cache still holds the group and the rule** (its deny comes from the login oracle) |

What the P2-6 arms do with the two oracles: A6 asserts the revocations on the **server** (`ipa group-show`, `user-show`, the member lists) and "the client has not been refreshed" with the **cache** oracle (ann is still in the sudo role group and still listed by `sudo -l` after the Go run, which never refreshes); it uses the **login** oracle only before the revocation, to assert that ann is allowed. No P2-6 arm asserts a client-side deny after a revocation; the login oracle's "deny at once" is K20's own measurement above, and the arms that assert the client's deny after a refresh are P2-7's (H1, H3, H4, H6). There is no natural expiry to wait for inside 300 s.

## How the numbers were taken

- **A sample is one `pilot reconcile …` process**, started from outside by the driver (a Go test that builds the candidate's binary and runs it) and timed from `exec` to exit. It contains everything an operator waits for: the preflight (`ansible-inventory`, `ansible --list-hosts`), the SSH connections (the lock's, the tunnel's, the FQDN and CA probes), the login, the live reads, the plan, the freshness reads, the entry playbook, the writes and the read after the writes. Nothing was taken out of the run to improve a number.
- **Two counts of the same run.** Pilot's result file gives HTTP requests (every POST of its client, the login included, the logout not), read commands and write commands (batch items counted one by one). The server's own logs, read between two marks taken around the run, give the same things without asking pilot: the access log's POSTs to `/ipa/session/json` (the logout included, the login not), the API log's commands by method (a batch's items counted once, the outer batch line counted as a batch request) and sshd's log (connections, command sessions, sessions that rode on a connection another session had already used). A gate fails a sample when pilot's and the server's write counts differ.
- **Entry playbook time** is the lifetime of pilot's `ansible-playbook` child that runs `freeipa-identity-auth-cache.yml` (the prepare in a run that writes, the probe in a run that does not), watched through `/proc` every 20 ms. It has its own column and is **not** subtracted from the wall time. The same watch gives the identity playbook's passes of a mixed run.
- **Restore.** Every mutation sample starts from the same VM snapshot: the server (both VMs for a mixed run) is reverted with `vm-target rollback`, then the guest clock is set from the controller. The lab was restored by snapshot revert, not by deleting objects, so uid and gid counters, entry cache and journal are what the snapshot held. No-diff samples change nothing (the server logs zero write commands and the journal's bytes are the same) and run back to back on the snapshot's state. "first" and "rerun" are separate samples: a rerun is the run after the first on the state the first left.
- **Percentiles** are nearest-rank (the value at rank ceil(p·n/100) of the sorted samples). A p95 is formal only from n ≥ 20 (plan §6); a smaller n is shown in parentheses and is only the largest of those few samples.
- **SSH connections** are sshd's `Accepted publickey` lines in the run's window ("new"), its `Starting session` lines ("sessions") and the sessions beyond the first on one connection ("reused"). The driver makes sshd log them (`LogLevel VERBOSE`, a drop-in written on the lab server after the baseline snapshot was restored and carried by every snapshot taken after that); pilot's own ssh uses `ControlPath=none`, so its connections are all new, and the reuse is the entry playbook's and the identity playbook's `ControlMaster`.
- **Correctness gates of the benchmark** (each has a case that must pass and cases that must fire in `live_perf_logic_unit_test.go`, and the `controls` scenario fires each against a real run built to break it): no-diff runs write nothing and leave the journal alone; a one-attribute run is one `user_mod` carrying that field and no `passwd`; a hundred creates are a hundred `user.create` and a hundred `user_add` at the server, every operation applied and the read after clean; a rerun writes nothing and runs no entry; pilot's and the server's write counts agree; the read saw every user and group the server holds; a delete removes exactly the declared objects.

## Recommendation on Phase 3 (for the maintainer; not a decision)

The plan's rule (§5, "規模與 go/no-go"): when the full central flow already meets 180 s, Phase 3 is not started on performance grounds and the mixed run is the steady state; when it does not, sections are moved one by one in the order of their share of the time. What these runs give to that rule:

1. **The Go engine did what Phase 2 was for.** The users-groups part of a reconcile is now a few seconds to half a minute at 120/40 (a hundred creates: p95 35.0 s), with a handful of HTTP round trips that do not grow with the data. What the old engine spent on users and groups is not in the mixed run's time any more.
2. **The full reconcile does not meet 180 s once the other sections are not tiny**: 544.0 s on the wide roster (21 hosts, 22 HBAC rules, 26 sudo rules, 120 users), and the identity playbook is 92 % of it. In its apply pass sudo takes 178.7 s and HBAC 108.7 s of 374.3 s, then host groups 35.9 s and hosts 32.8 s; users, groups, netgroups and passwords together are about 9.1 s. On the narrow roster at 120 users it is 108.3 s, inside the target.
3. **A second cost that Go did not remove**: at 1,000 users the identity playbook still spends about 98.3 s per pass on per-user normalization and gates (no API calls), which the engine variable does not skip; the mixed run at 1,000/200 takes 406.6 s although Go's part of it is 15 s.

**Recommendation.** (a) Phase 3 is justified on performance grounds **if the production roster's hosts, HBAC and sudo sections are about the size of the wide lab roster or larger**; this lab cannot say what production's counts are (the last of the three historical runs of plan §1 had 1,381 API calls, 685 of them users and groups: 118 `user-add`, 118 `user-mod`, 118 `user-show`, 84 `passwd`, 130 `group-add-member`, 117 `user-enable`). Measure the mixed run once on a production-shaped roster first; that is cheap with this driver. (b) If Phase 3 starts, the order by time share is **sudo, then HBAC, then host groups and hosts**; netgroups, passwords, users and groups are small. Each as its own sub-phase with the plan's exit criteria. (c) Independently of Phase 3, and cheaper: the users and groups normalization and gate tasks that the Go engine already made redundant could be skipped by the same engine variable (at 1,000 users that is about 98.3 s of a 157.9 s pass; at 120 users about 6.2 s of 43.1 s); it is a playbook change with its own regression and a `vm-target` chain, not a Go change. (d) Phase 4 for the users-groups scope does not depend on this decision.

## Not covered / limits

- **This is a lab, not production (spec X2 is still open).** The server is a 2-vCPU, 6 GiB VM on a libvirt bridge of the same 12-core host as the controller, with about 0.5 ms ping and 0.25 s for a new ssh connection; the host was shared with six other running VMs, its memory was heavily swapped and its one-minute load average was between 1.4 and 4.6 when a sample started or ended. FreeIPA 4.13.4 on AlmaLinux 9.8, one server, no replica, one enrolled Ubuntu client. A production server with a real RTT, more CPU and a replica will give other seconds. What carries over is the structure of the numbers: how many HTTP round trips and ssh connections a run makes (they do not grow with the data), which phase grows with the data (the full reads), and which part of a mixed run does not shrink with it.
- **The starting state was not empty**: the baseline snapshot held 138 active users, one preserved user and 88 groups from earlier lab work; the engine read all of them in every run, so "120/40" means 120 users and 40 groups made by the benchmark on top of that, and "1,000/200" means 1,000 and 200 on top of that (1,139 users and 488 groups read at the end: the groups include one history marker group per created group and per earlier lab group).
- **Samples**: n = 20 for the p95 rows of the users-groups scope (no-diff, one attribute, a hundred creates). The rows that say (n) in parentheses have fewer samples and are not formal p95 figures: the hundred modifies (5), creates with initial passwords (3), the batch-limit sweep (5 per limit), the preview (3), the mixed runs (1 to 3, each takes 2 to 10 minutes), the 1,000/200 attribute, delete and big-group runs, the profile (1 run per dataset) and the legacy engine (1 per scenario). The mixed run's 180 s target is judged on far larger differences than a p95 needs (the wide roster's runs are three times the target), not on a p95.
- **Entry time was not observed in 4 of the 218 runs that ran an entry or a probe** (the `/proc` watch classifies a child when it first sees it, and caught that child between fork and exec, while its command line was still pilot's). Their wall times are unaffected; the entry columns are medians of the runs where it was seen. Changing the watch to re-read until exec would need a new candidate and every number re-taken, which this item did not do.
- **The identity playbook's profile** (`profile_tasks`, one pass of the playbook by itself with the Go engine variable set) lists the slowest tasks and a bucketing by what the task's name says it is about. It is a reading of the names, not of the playbook's structure.
- **The wide roster is a bigger lab roster, not a copy of production's**: 21 hosts in 9 host groups, 22 HBAC rules and 26 sudo rules with 6 command groups. The production roster's counts are not known to this record (plan §1 gives the historical API-call mix of the identity run).
