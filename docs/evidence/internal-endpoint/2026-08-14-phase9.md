## Real bugs found and fixed

All four were caught by writing
`edit_automation_driver_internal_endpoint_test.go` and running it for real against the
actual `editRouterModel` (not a mock) — none were visible from `go build`/`go vet` alone.

1. **TLS sink editing was gated behind a condition that could never be satisfied.**
   `pushInternalEndpointTLSMenu`'s "sink" menu item originally required
   `route.mode == direct && tls.mode == freeipa` before allowing entry — but
   `checkIEPDirectTLSSink` (internal/inventory, spec.md §22) requires `tls.sink` to
   already be fully populated the instant `tls.mode` becomes `freeipa` on a direct
   route. That made the two gates mutually impossible: you could never populate sink
   (blocked until mode=freeipa) and could never set mode=freeipa (blocked until sink is
   populated) — a hard deadlock with no path through the wizard at all, for a human or
   for automation. Confirmed via a standalone `SimulateSetInternalEndpoint` probe:
   ```
   found=true err=<nil> violations=[[tls.sink.cert_file] ... is required
   [tls.sink.key_file] ... is required [tls.sink.reload.mode] ... must be systemd, got ""
   [tls.sink.reload.unit] ... is required]
   ```
   Fixed by gating sink access on `route.mode == direct` alone, so sink can be prepared
   *before* flipping mode to freeipa (`edit_tui_internal_endpoints.go`,
   `pushInternalEndpointTLSMenu` case 2).

2. **The mode-flip itself silently discarded any sink/port already entered.**
   `pushInternalEndpointTLSModeField`'s mutate only preserved existing `tls.port`/
   `tls.sink` when the *previous* mode was already `"freeipa"` — so sink data entered
   while mode was still `"disabled"` (the only order fix #1 makes possible) was
   silently dropped the moment mode flipped to `"freeipa"`, and the write was then
   rejected by the same `checkIEPDirectTLSSink` gate as fix #1 (now for a different
   reason: the sink the user just entered was gone). Fixed by preserving `port`/`sink`
   unconditionally when moving to `"freeipa"`, regardless of the previous mode.

3. **Menu-label substring collision introduced by fix #1's own wording.** The first
   attempt at fix #1's warning text ("...僅 route.mode=direct 適用") accidentally
   contained the substring `"mode"`, which the automation driver's `d.choose(r, "mode")`
   matches by unique-substring — with two menu items now containing `"mode"` (the
   `mode：` item and the reworded `sink（...route.mode=direct...）` item),
   `uniqueItemIndex` correctly refused to guess and returned `label "mode" is
   ambiguous`. Fixed by rewording to "...僅 direct route 適用" (no `"mode"` substring).

4. **`setInternalEndpointRouteDirect`'s branch was a no-op `if`-init bug.** The
   original code was:
   ```go
   if err := d.choose(r, "從 inventory host 解析"); targetHost == "" {
       value = targetAddress
       if err := d.choose(r, "手動輸入 IP"); err != nil { return err }
   } else if err != nil { return err }
   ```
   The `if`-statement's init clause (`d.choose(r, "從 inventory host 解析")`) executes
   *unconditionally*, regardless of the `targetHost == ""` condition that follows it —
   so a `target_address`-only call (no `target_host`) always selected the wrong menu
   item first, landed on the "從 inventory host 解析" value screen, and then tried to
   `choose("手動輸入 IP")` on that (now a text-input, not a select) screen:
   `cannot choose "手動輸入 IP" on iep.route.direct.value screen`. This made
   `set_internal_endpoint_route_direct` with a literal `target_address` completely
   non-functional. Fixed with a plain `if targetHost == "" { ... } else { ... }`.

## Real scenarios validated (`edit_automation_driver_internal_endpoint_test.go`)

All four drive the actual `automationDriver`/`editRouterModel` (the same machinery
`pilot edit --actions <scenario.json>` and the MCP `pilot_edit_apply` tool use) end to
end, then assert on the resulting `internal-endpoints.yaml` bytes via
`internal/inventory`'s own readers — not a reimplementation of the TUI's logic.

1. `TestEditAutomationDriverInternalEndpointFlow_CreateManifestAndDirectEndpoint` —
   `create_internal_endpoint_manifest` -> `create_internal_endpoint` (direct route) ->
   `set_internal_endpoint_dns` -> `set_internal_endpoint_tls_sink` ->
   `set_internal_endpoint_tls_freeipa` (port=8443). Confirms `dns.zone`/`dns.ttl`,
   `route.mode=direct`/`route.target.inventory_host`, and the full `tls.mode=freeipa`
   + `tls.port` + `tls.sink.{cert_file,key_file,key_owner,key_group,key_mode,
   reload.unit}` shape land correctly and in the order the sink-before-mode
   constraint (bug #1/#2 above) actually requires.
2. `TestEditAutomationDriverInternalEndpointFlow_ReverseProxyRouteAndState` —
   `set_internal_endpoint_route_proxy` (https upstream, `upstream_tls_verify=true`,
   SNI) confirms `route.proxy.inventory_host`, `route.upstream.{scheme,inventory_host,
   port}`, and `route.upstream.tls.{verify,server_name}` all land correctly.
   `set_internal_endpoint_state` (present -> absent) is then confirmed to be **safely
   rejected**: `checkIEPDeleteSafety` requires `safety.allow_endpoint_delete: true`,
   which no TUI screen can set (identical posture to freeipa-dns's own zone-delete
   gate, see `TestEditAutomationDriverDNSFlow_SwitchRecordValueSourceAndZoneState`) —
   `state` still reads `"present"` afterward, exactly like a human hitting the same
   violation banner in the interactive wizard would see.
3. `TestEditAutomationDriverInternalEndpointFlow_RouteDirectByAddressAndTLSDisabled` —
   `set_internal_endpoint_route_direct` with a literal `target_address` (no
   `target_host`) confirms `route.target.address` is set and `route.target.
   inventory_host` is cleared (bug #4 above); `set_internal_endpoint_tls_disabled`
   confirms `tls.mode=disabled`.
4. `TestEditAutomationDriverInternalEndpointFlow_ValidationRejectsBadInput` — every new
   `validate*` function (`validateCreateInternalEndpoint`,
   `validateSetInternalEndpointState`, `validateSetInternalEndpointDNS`,
   `validateSetInternalEndpointRouteDirect`, `validateSetInternalEndpointRouteProxy`,
   `validateSetInternalEndpointTLSFreeIPA`, `validateSetInternalEndpointTLSSink`,
   `validateFQDNOnly`) rejects its documented bad-input cases, including the
   `upstream_tls_verify` required-iff-https/forbidden-iff-http rule (spec.md
   §12.4.1/§12.4.4).

## MCP inspect coverage (`mcp_edit_tools_test.go`)

`TestInspectHandler_InternalEndpointsIncludeResolvedIPAndOmitWhenNotRequested` — a
direct-mode and a reverse_proxy-mode endpoint (the latter with `upstream.tls.verify`/
`server_name` and a full `tls.sink`) are read back through `pilot_edit_inspect`'s
`include_internal_endpoints` flag: `route.target`/`route.proxy`/`route.upstream`'s
`inventory_host` references are cross-resolved to `resolved_ip` against `hosts.yml`
exactly like `include_dns` already does for DNS record targets; a literal
`upstream.address` (no inventory host) correctly resolves to no IP; `include_internal_
endpoints: false` returns `nil`. No secret/private-key material appears anywhere in
the output (the manifest schema itself carries none — only file paths and POSIX
ownership metadata for the sink).

While writing this test, discovered and fixed a second real gap:
**`internal-endpoints.yaml` was never in `managedFileEntries`'s explicit file list**
(`edit_workspace_files.go`), unlike `freeipa-dns.yaml` and `hosts.yml` — so
`buildInspectInternalEndpoints` silently returned zero endpoints regardless of what the
manifest actually contained, for both `pilot_edit_inspect` and the `pilot://
internal-endpoints` resource. Fixed by adding the missing `addFile("internal-endpoints.
yaml", false)` call.

## Workspace completeness coverage (`workspace_completeness_test.go`)

`checkInternalEndpointCompleteness` runs `ValidateInternalEndpointManifestFile` with
`Hostvars`/`ReverseProxyHosts` built from `hosts.yml` (static-only, matching spec.md's
"validator must mirror apply gates" posture — `EnrolledHosts`/`FreeIPADNSZones`/
`LedgerFQDNs`/`PreviousRoutes` are deliberately left nil, since those require live host
state or the ownership ledger that this offline sweep has no business asserting). Four
new tests confirm: no row when the manifest doesn't exist (opt-in feature, same as
`freeipa-dns.yaml` having no row of its own today); an unresolved
`route.target.inventory_host` is reported by name; a valid manifest with both a direct
and a reverse_proxy endpoint reports OK; a `route.proxy.inventory_host` that lacks the
`reverse-proxy` role is reported.
