## Real bugs found and fixed

1. **A genuine `dict has no attribute` AttributeError on the very first real run** — the
   normalization block's `sink`/`reload`/`upstream`/`upstream_tls` variables were built with
   dot-notation (`sink.cert_file`) on a `| default({})`-produced literal empty dict.
   Confirmed live (2026-08-14): endpoint B (`aaa.xxx.apps.pilot.internal`, tls.disabled —
   genuinely has no `tls.sink` key at all) crashed the whole normalization loop with
   `object of type 'dict' has no attribute 'cert_file'`, even though endpoint A (which DOES
   have a real `tls.sink`) worked fine. This is the same ansible-core 2.19
   lazy-templated-dict class of bug already documented in this codebase's own memory for
   `freeipa-dns-apply.yml`'s `.get('values')` convention — a `default({})` result is a
   genuine Python dict literal, not the wrapped type Jinja normally falls back to Undefined
   for. Fixed by rewriting every optional nested-dict access in the normalization block
   (route/tls/sink/reload/upstream/upstream_tls, and their nested keys) to `.get(key,
   default)` instead of dot-notation, everywhere a key might genuinely be absent.
2. **The exact same bug reappeared one layer down, in the new vhost-render task file's own
   `fail_msg`**, once idempotency-related gating made `iep_nginx_test` a skipped-task
   result on a clean rerun: `{{ iep_nginx_test.stdout }}` inside an `assert`'s `fail_msg` is
   apparently finalized/rendered even when the assertion passes, and a skipped result
   lacks `.stdout`/`.rc` via dot-notation. Fixed the same way — `.get('stdout', '')` /
   `.get('rc', -1)` throughout that file's `when:`/`fail_msg` references to
   `iep_nginx_test`.
3. **Hand-rolled stat+copy+remove "rollback snapshot" logic broke idempotency —
   `changed` was never 0 on a clean rerun.** The first idempotency check showed
   `changed=6` on an otherwise no-op rerun: the snapshot-create/snapshot-remove/reload
   tasks ran (and reported changed) unconditionally on every single pass, since the
   snapshot `.bak` file gets created fresh and then unconditionally deleted every run
   regardless of whether the rendered vhost content actually differed. Fixed by replacing
   the entire hand-rolled mechanism with `ansible.builtin.template`'s own native `backup:
   true` — it only creates a backup file, and only reports `changed: true`, when the
   rendered content genuinely differs from what's on disk; nginx -t/reload/rollback are now
   all gated on `iep_vhost_render.changed`, so a true no-op rerun does none of them.
   Confirmed: a subsequent rerun reported `changed=0 failed=0` on all 3 hosts.
4. **`freeipa-dns-apply.yml` must actually run before internal-endpoint's DNS write
   (same lesson as Phase 6, re-confirmed here)** — the first real apply attempt failed
   with `DNS zone not found` until the zone was created via a real
   `freeipa-dns-apply.yml` run against the same manifest used for C7/C8's cross-check.
5. **`docs/verification/internal-endpoint.md` C27/C32 ran on the wrong host** — same class
   of bug Phase 5/6 already found and fixed for C14/C15/C16: both rows read the rendered
   nginx vhost config file, which lives on the **proxy** host, but defaulted to per-host
   dispatch on `freeipa-server`. Caught during this round's own spec authoring (before
   ever running `pilot verify` against the live topology) by recognizing the same pattern.
   Fixed with `scope: aggregate` + `ansible <host> -m shell` dispatch to
   `$PILOT_VAR_TEST_EXPECTED_CERT_OWNER` (which, per spec.md §15, is exactly the proxy host
   for a reverse_proxy endpoint — the same variable C11/C13/C14/C15/C16 already use for
   cert ownership).

### 2. DNS — every route points at the right owner, never the upstream (spec.md §11.4, C4/C5)

```
$ dig +short direct.apps.pilot.internal @127.0.0.1        → 192.168.122.7 (p7-app01, direct target)
$ dig +short aaa.xxx.apps.pilot.internal @127.0.0.1        → 192.168.122.7 (p7-app01, nested direct target)
$ dig +short proxy.apps.pilot.internal @127.0.0.1          → 192.168.122.8 (p7-proxy01, NOT the upstream)
```

### 3. Endpoint C — reverse_proxy + HTTP upstream, real client traffic through nginx

Rendered vhost (`/etc/nginx/conf.d/pilot-internal-endpoint-proxy-apps-pilot-internal.conf`
on p7-proxy01): `proxy_pass http://192.168.122.7:18080;` with no `proxy_ssl_*` directives
(spec.md §13.1 — HTTP upstream must not generate any).

```
$ curl -sS https://proxy.apps.pilot.internal/ --resolve proxy.apps.pilot.internal:443:192.168.122.8
pilot-endpoint-ok
```

No `-k`/`--insecure` needed — real FreeIPA-issued frontend cert
(`subject=O=IPA.PILOT.INTERNAL, CN=proxy.apps.pilot.internal`, `issuer=CN=Certificate
Authority`), real forwarding to the disposable HTTP backend on `app01:18080`.

### 4. Endpoint D — reverse_proxy + insecure HTTPS upstream, real client traffic through nginx

Rendered vhost: `proxy_pass https://192.168.122.7:18443;`, `proxy_ssl_server_name on;`,
`proxy_ssl_name legacy-backend.internal;`, `proxy_ssl_verify off;` — no
`proxy_ssl_trusted_certificate` (correct: verify=false doesn't need one).

```
$ curl -sS https://legacy.apps.pilot.internal/ --resolve legacy.apps.pilot.internal:443:192.168.122.8
pilot-endpoint-ok
```

Backend cert genuinely self-signed, NOT FreeIPA-issued (`subject=issuer=CN=proxy-backend-
selfsigned.selfsigned.invalid`) — confirms nginx accepted an untrusted upstream cert
because `tls.verify: false` was explicitly declared, not because it silently downgraded to
plaintext:

```
$ echo | openssl s_client -connect 127.0.0.1:18443 -brief 2>&1 | grep -i 'Protocol version'
Protocol version: TLSv1.3
```

  not separately proven live this round.
