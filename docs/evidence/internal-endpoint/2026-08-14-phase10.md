## Real bugs found and fixed

1. **`internal-endpoint-ledger-entry.yml`'s `delegate_to` crashed on any non-TLS
   endpoint in the same manifest as a TLS one.** `cert_owner` is `""` for a
   `tls.mode: disabled` endpoint (correct — it has no certificate), but
   `delegate_to: "{{ iep_endpoint.cert_owner }}"` is templated by ansible-core for
   *every* loop item regardless of the task's own `when: iep_endpoint.tls_mode ==
   'freeipa'` — an empty `delegate_to` host is a hard error
   (`Empty hostname produced from delegate_to`), not a skip. Every prior phase's
   manifest happened to have either all-TLS or a TLS/no-TLS pair tested in *separate*
   runs, so this never surfaced until this round's single 5-endpoint manifest mixed
   endpoint A (disabled) into the same reconcile as B/C/D/E (freeipa). Fixed by falling
   back to `inventory_hostname` (always valid) when `tls_mode != 'freeipa'`, since the
   task's own `when` already means that value is never acted on.
2. **An omitted `tls.port` rendered `listen 0 ssl` instead of the documented "scheme
   default 443".** `internal-endpoint-apply.yml`'s reconcile play defaulted
   `tls_port: "{{ tls.get('port', 0) }}"` — since `0` is a *defined* value (not
   Jinja `Undefined`), the nginx template's own `{{ iep_endpoint.tls_port |
   default(443) }}` never overrode it. Confirmed live: endpoint C (no explicit
   `tls.port`) rendered a literal `listen 0 ssl;`/`listen [::]:0 ssl;` — nginx would
   have rejected this the moment `--check` stopped hiding it from a real `nginx -t`.
   Fixed by defaulting to `443` directly, matching the Phase 9 TUI's own already-documented
   "0/absent means 443" contract.
3. **`pilot internal-endpoint validate` had never been built, and its absence was
   masking a real false-positive in the spec's own C1 row.** `docs/verification/
   internal-endpoint.md`'s C1-C3, C8, C30 rows were all authored in Phase 1 against a
   CLI shape (`pilot internal-endpoint validate --manifest ... [--print-normalized]
   [--freeipa-dns-manifest ...]`) that no phase since (2-9) had actually implemented —
   confirmed live: `pilot internal-endpoint validate` returns cobra's generic
   `Error: unknown command "internal-endpoint" for "pilot"` (rc=1). **C1's own probe
   does `[ "$rc" -ne 0 ] && grep -qi unknown` → "rejected"** — cobra's stock error text
   happens to contain the word "unknown", so C1 has reported `pass` in every one of
   Phases 6-8's evidence rounds, and every one of those passes was a false positive, not
   a working check (C2/C3/C8/C30 check for different keywords — "duplicate", "ownership
   conflict", "verify" — none of which appear in cobra's stock message, so those rows
   correctly failed instead). Built the real CLI
   (`cmd/pilot/cmd/internal_endpoint_cli.go`, `internal_endpoint_cli_test.go`) as a thin
   wrapper over `internal/inventory`'s already-tested Go validator/normalizer — no new
   validation logic, just wiring. Authored the 5 fixture manifests these rows'
   probes reference (`playbooks/test/fixtures/internal-endpoint-manifests/`), which
   also did not previously exist.
4. **C8 (and C21/C23/C24) had an independent `pilot verify` scoping bug, only exposed
   once the CLI in bug 3 actually existed.** `pilot internal-endpoint validate` and
   `pilot reconcile` are controller-side commands (they read local
   `manifest_fixture_dir`/`freeipa_dns_manifest_path` paths, or drive `ansible-playbook`
   themselves) — but C8/C21/C23/C24 were never marked `scope: aggregate`, so `pilot
   verify` dispatched them per-host to `freeipa-server`, where `pilot` isn't installed
   at all (`rc=127`, command not found). This is the exact same class of bug this file
   has now fixed 6 times (C7, C9, C10, C14-C16, C27, C32, and now C8/C21/C23/C24) —
   every one of them was "this row assumes it runs on the controller, but the spec
   author forgot `scope: aggregate`". Fixed all 4. C8 now genuinely passes; C21/C23/C24
   still correctly fail (the *feature* — a non-interactive `pilot reconcile
   internal-endpoint --manifest/--ledger` surface — genuinely does not exist; see Known
   follow-up below), but now for the right reason (`rc=1: unknown flag`, not `rc=127`
   dispatched to the wrong host entirely).
5. **Operational gotcha (not a code bug): a stale globally-installed `pilot` binary at
   `~/bin/pilot` shadowed every source change.** `pilot verify`'s controller-scoped
   probes invoke the bare `pilot` command (PATH-resolved), not `go run ./cmd/pilot` —
   so building the CLI in bug 3 had *zero* effect on real verify runs until `~/bin/pilot`
   was rebuilt from the current source tree. Worth remembering for any future round
   that adds a new CLI surface and tests it via `pilot verify`.
6. **Test-design pitfall (not a project bug): reusing one endpoint's real cert as
   another endpoint's "verified upstream" backend requires an explicit SNI override.**
   Endpoint D's upstream is `p10-proxy:8443` (endpoint B's own real FreeIPA cert,
   subject `CN=tls.apps.pilot.internal`) — the auto-derived SNI (no explicit
   `tls.server_name`) resolves to `p10-proxy`'s own canonical `ansible_fqdn`
   (`p10-proxy.ipa.pilot.internal`), which the reused cert's SAN never matches, so the
   real local-backend-readiness check correctly failed closed with a genuine TLS
   hostname-verification error (spec.md §12.4.6 working exactly as designed). Fixed by
   setting `upstream.tls.server_name: tls.apps.pilot.internal` explicitly to match the
   cert actually being reused — not a defect, but a reminder that this spec's own
   hostname-verification enforcement is real and will catch a sloppily-designed test
   fixture just as readily as a real misconfiguration.
7. **Operational gotcha: `vm-target wire` assumes a root SSH login.** Its `sed -i
   /etc/hosts` script runs as whatever user SSH logs in as, with no `sudo` prefix — the
   `cloud-user`/`ubuntu` non-root logins this round's 3 VMs use (matching every prior
   phase's own convention) hit `Permission denied`. Worked around by replicating the
   same idempotent marker-block logic manually via `vm-target exec ... -- sudo sh -c
   '...'`. Not fixed in code this round (a `--sudo` flag or auto-detection would be the
   real fix) — noted for a future session.
8. **Operational gotcha: declaring `--group all=<hosts>` collides with the implicit
   `all` group `vm-target run` already provides**, producing `Gate: a freeipa-server
   host is present in inventory` failures that look like a missing-group problem but are
   actually a self-referential `all: children: all:` YAML structure. Every host is
   already a member of `all` by virtue of being listed under the top-level `all.hosts:`
   block in any `--group` invocation — there is never a reason to also declare a group
   literally named `all`.

## Follow-up round — C9 DNS resolver baseline (same day, 2026-08-14)

- Candidate: working tree on top of the round above, plus this round's own fixes.
- Environment: 3 fresh disposable `pilot vm-target` KVM VMs (independent of the
  5-endpoint topology above — not yet re-combined into a single run).
  - `p11-ipa` — AlmaLinux 9, `cloud-user`. FreeIPA server, self-pointing DNS case.
  - `p11-el` — AlmaLinux 9, `cloud-user`, plain (no FreeIPA anything). Exercises the
    NetworkManager resolver path fresh.
  - `p11-debian` — Ubuntu 24.04, `ubuntu`, plain. Exercises the systemd-resolved path
    fresh, and is the regression check against the original 2026-07-31 evidence.
- Scope: implement C9 (fleet-wide DNS resolver baseline), one of Phase 10's own two
  "Known follow-up" items, per the plan the user asked for explicitly after reviewing
  the Phase 10 gap list.

### The fix

1. Extracted `freeipa-dns-client-apply.yml`'s resolver-configuration logic (Debian
   systemd-resolved drop-in + resolv.conf, EL NetworkManager dns4, the `dig`-based
   functional proof, and the resolv.conf rescue/rollback) into a new shared
   `playbooks/apply/tasks/freeipa-dns-client-resolver.yml`, mirroring
   `tasks/freeipa-ca-trust.yml`'s existing two-caller sharing convention exactly
   (self-contained: no dependency on the including play's own `vars:`/`handlers:`,
   using an inline `when: <task> is changed` restart instead of `notify:` — a
   handler notified from an included task file would also need to be defined in
   whichever play includes it, an unnecessary coupling `tasks/freeipa-ca-trust.yml`
   never had either).
2. `freeipa-dns-client-apply.yml` itself now just keeps its stage gates and calls
   `include_tasks: tasks/freeipa-dns-client-resolver.yml`.
3. Wired the same shared file into `internal-endpoint-apply.yml`'s **first**
   (fleet-wide, `hosts: all`) play, alongside the existing C10 CA-trust task — not
   the second (single-host `freeipa-server`) play, where the old C9 placeholder had
   actually lived. That placement was itself a bug: a task in the single-host
   reconcile play can only ever run on the freeipa-server, never on the other
   managed hosts C9's own probe checks — found while reading the code to plan this
   fix, before touching anything.
4. Fixed C9's own probe from `resolvectl status` (a Debian-only tool; doesn't exist
   on EL9 by default) to a portable `getent hosts <freeipa-server-fqdn>` check
   (NSS-based, identical on both OS families) — added a new required input,
   `test_freeipa_server_fqdn`.

### Real bugs found and fixed

1. **The NetworkManager discovery command was silently skipped under `--check`,
   crashing the very next task.** `ansible.builtin.command: nmcli -t -f NAME,DEVICE
   connection show --active` had no `check_mode: false` — under `--check` it never
   runs (command modules aren't idempotency-aware, so they default to skip), leaving
   `freeipa_dns_client_nm_active` undefined and the next task's
   `freeipa_dns_client_nm_conn is defined` assert failing on p11-el/p11-ipa. This is
   the exact same class of bug already documented in `tasks/freeipa-ca-trust.yml`'s
   own header comment (a read-only diagnostic needs `check_mode: false` to actually
   run under `--check`) — the pre-extraction `freeipa-dns-client-apply.yml` had this
   same bug the whole time; nobody had ever run `--check` against it before (the
   original 2026-07-31 evidence only shows real, non-dry-run applies). Fixed by
   adding `check_mode: false`.
2. **C3's own probe never survives on EL.** C3 checks for a `pilot-freeipa-dns-client`
   comment marker in `/etc/resolv.conf` — correct evidence on Debian, but on EL,
   `nmcli device reapply` (which the very next task in the same reconcile always
   runs after any `dns4` change) makes NetworkManager regenerate `/etc/resolv.conf`
   from its own persisted connection profile, stamping a `# Generated by
   NetworkManager` header and dropping any comment we wrote. Confirmed this is a
   probe-design bug, not a functional defect: the regenerated file's actual DNS
   content (`nameserver 192.168.122.5`, `search ipa.pilot.internal`) was correct,
   and C6's real `dig +short ipa1.ipa.pilot.internal` functional check passed
   throughout. Fixed C3 to check the NetworkManager connection profile's own
   persisted `ipv4.ignore-auto-dns` field (only pilot ever sets this to `yes`) when
   `nmcli` is present, falling back to the original marker check on Debian.
