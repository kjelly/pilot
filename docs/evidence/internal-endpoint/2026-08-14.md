## Real bugs found and fixed

1. **`ipa-getcert request -g`/`-G` are NOT group flags.** The first design attempt passed
   the manifest's `tls.sink.key_group` to `-g` and a hardcoded cert group to `-G`,
   guessing these meant "key group"/"cert group" by analogy with `-o`/`-O` (owner). Real
   `ipa-getcert request --help` (confirmed live, 2026-08-14) shows `-g BITS, --key-size`
   (key generation size) and `-G TYPE, --key-type` (RSA/EC) — passing a manifest group
   name like `"root"` to `-g` produced `No support for generating "root" keys. Known key
   types include: RSA EC`. `getcert-request(1)` has **no dedicated group flag at all** —
   `-o`/`-O` take a single chown-style `OWNER` string. Fixed by using
   `-o key_owner:key_group` / `-O root:root` (colon-combined), confirmed via
   `getcert list` showing `owner=root:root` on the real tracked request.
2. **Real DNS zone must exist before internal-endpoint's own DNS-write tasks can
   succeed — contracts/internal-endpoint.yaml's `freeipa-dns` planOnly dependency is not
   automatic.** The first real apply attempt failed with `ipa: ERROR:
   apps.pilot.internal.: DNS zone not found` — a hand-written freeipa-dns manifest
   *fixture* (used only for internal-endpoint's own C7/C8 preflight cross-check) does not
   itself create the zone; `freeipa-dns-apply.yml` must be run first against the same
   manifest. Not a code bug, but a real ordering dependency worth recording: any topology
   exercising internal-endpoint's direct-route DNS write needs a prior
   `freeipa-dns-apply.yml` run.
3. **Pre-seeding a placeholder self-signed cert/key so a systemd consumer can start before
   certmonger issues the real one silently defeats certmonger's own request logic.** The
   test-fixture playbook originally generated a placeholder cert at `cert_file`/`key_file`
   before the reconciler ran. `ipa-getcert request -f -k` against an already-present,
   still-valid cert/key pair **adopts it for tracking** (`status: MONITORING`) rather than
   immediately requesting a fresh one — confirmed live: `getcert list` showed `MONITORING`
   while `openssl x509 -in server.crt -noout -subject -issuer` kept showing
   `CN=placeholder.invalid` indefinitely; the real FreeIPA-issued cert never landed. Fixed
   by having the fixture deploy the systemd unit **enabled but not started**, and only
   starting it after the real cert exists — `getcert-request(1)`'s existing-file adoption
   behavior is a genuine certmonger design point, not a bug, but it made the "placeholder
   cert to unblock service startup" strategy actively wrong for this use case.
4. **A previously-unknown, project-wide `pilot verify` bug: per-host Spec v2 rows never
   actually received their `$PILOT_VAR_*` inputs.** `posixEnvironmentPrefix` (
   `internal/tools/per_host_verify.go`) built a same-line shell prefix —
   `PILOT_VAR_X='val' <probe script>` — which POSIX shells apply only to the **environment
   of that one command's exec()**, not to that same command's own `"$VAR"` argument
   expansion (the shell expands arguments using its existing variable table before
   splicing in the temporary child environment), and never persists to later lines of a
   multi-line probe at all. Confirmed directly: `sh -c 'FOO=bar echo "$FOO"'` prints an
   empty line, on every POSIX shell, unconditionally. This meant every per-host row
   referencing `$PILOT_VAR_*` had always evaluated it as empty — invisible whenever the
   row's `expect` also happened to reduce to comparing two empty strings (a common shape:
   `if [ "$got" = "$PILOT_VAR_X" ]; then echo match; else ...`, which is `[ "" = "" ]` →
   true → false-positive PASS when the real lookup also failed for an unrelated reason).
   Fixed by rendering `export PILOT_VAR_X='val'` one per line instead of a single-command
   prefix — a real, persistent shell variable visible to every later line of the same
   `/bin/sh -c "..."` script. Added `TestPOSIXEnvironmentPrefixVisibleToSameScript`
   (`internal/tools/per_host_verify_test.go`), which runs the actual generated prefix
   through a real `/bin/sh` so a regression back to the single-command form fails loudly
   instead of only being catchable by eyeballing generated shell text. **This bug is not
   specific to internal-endpoint** — it affects every Spec v2 verification file with
   per-host rows anywhere in the project; a broader audit of existing specs for rows that
   may have been silently false-passing is a worthwhile follow-up (see below).
5. **Once bug 4 was fixed, two more previously-masked bugs surfaced in
   `docs/verification/internal-endpoint.md`'s own probes:**
   - **C7** read `d.get('zones', [])` on the freeipa-dns manifest's top-level dict, but a
     real freeipa-dns manifest nests zones under `dns.zones`, not a top-level `zones` key
     — this always printed `zone-not-found`, masked until now by bug 4 already making the
     whole probe fail with `open('')` first. Fixed to `d.get('dns', {}).get('zones', [])`
     with the effective `records_mode` correctly falling back to `dns.defaults`.
   - **C7 also ran on the wrong host.** `freeipa_dns_manifest_path` is a path on the
     machine driving ansible (the same file `internal-endpoint-apply.yml`'s own
     `ansible.builtin.include_vars` reads, which always resolves on the control node
     regardless of the play's `hosts:`), not on a managed host — per-host dispatch tried
     to open it on the remote VM and got `FileNotFoundError`. Fixed with `scope: aggregate`.
   - **C9/C10** grepped ad-hoc output for `| SUCCESS`, but `ansible -m command`/`-m shell`
     ad-hoc runs always report `| CHANGED` (or `| FAILED`), never `| SUCCESS` (that label
     is only for idempotent-aware modules like `ping`) — this always undercounted to 0,
     also masked by bug 4 (a broken `$PILOT_VAR_PILOT_INVENTORY_PATH` failed first, for an
     unrelated reason). Fixed by counting `| rc=0` instead. C10 now genuinely passes
     (`all 2 hosts ok`, confirming the Phase 3 CA-trust baseline really is on both hosts);
     C9 still correctly fails (`got=1 want=2`) — that row's own `resolvectl status`
     exit-code check isn't portable to AlmaLinux (which doesn't ship systemd-resolved by
     default), and C9's underlying mechanism is unimplemented Phase-1 placeholder logic
     regardless — left as a known follow-up, not blocking Phase 6.

### 2. Renewal reload hook — real, graceful, same PID

```
$ systemctl show -p MainPID --value pilot-endpoint-direct.service
10485
$ getcert resubmit -f /etc/pilot-endpoint/direct/server.crt
Resubmitting "20260814012424" to "IPA".
$ systemctl show -p MainPID --value pilot-endpoint-direct.service   # after resubmit completes
10485
$ journalctl -u pilot-endpoint-direct.service --no-pager -n 5
Aug 14 01:25:02 ... systemd[1]: Reloading pilot-endpoint-direct.service ...
Aug 14 01:25:02 ... python3[10485]: reloaded TLS context
Aug 14 01:25:02 ... systemd[1]: Reloaded pilot-endpoint-direct.service ...
```
Same PID before and after, journal proves the post-save hook fired `systemctl reload`
and the service's own SIGHUP handler rebuilt its TLS context — a real, non-destructive
reload, not a restart. A real `curl` after the reload still served
`pilot-endpoint-ok` over TLS.

  freeipa-dns-client-apply.yml's resolver tasks via a shared include).

  Ansible-side gate IS real and independently proven via scenario 4 above.
