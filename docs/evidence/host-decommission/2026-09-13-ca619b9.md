## 1. Reusing the proven workspace — 3 stale values found in the copied config

Bringing up a fresh `docs/topologies/minimal-poc-topology.yaml` assigns each VM a new
DHCP IP; copying round-31's workspace verbatim carried over **stale IPs from round-31's
own assignment**, all now silently valid-looking (they matched *some* host in the new
topology, just not the right one):

- `group_vars/freeipa.yml`'s `freeipa_server_ip: 192.168.122.6` — round-31's
  `freeipa-server` IP, which under the fresh topology became `client-vm`'s IP. This made
  `freeipa-server-apply.yml` pin `client-vm.ipa.pilot.internal` into `freeipa-server`'s own
  `/etc/hosts` as `ipa1.ipa.pilot.internal`, and `ipa-server-install` correctly refused:
  `"The host name ipa1.ipa.pilot.internal does not match the primary host name
  client-vm.ipa.pilot.internal"`. Fixed to the real `freeipa-server` IP
  (`192.168.122.4`); confirmed clean after a `vm-target topology reset` (to clear the
  partial state the failed attempt left) + re-apply.
- `group_vars/dashboard.yml`'s `thanos_query_target_host` and
  `group_vars/audit-log-forwarding.yml`'s `siem_forward_host` both still said
  `192.168.122.4` — round-31's `nexus` IP, which under the fresh topology became
  `freeipa-server`'s IP. Fixed both to the real `nexus` IP (`192.168.122.5`).
- `hosts.yml`'s `client-vm` entry was missing `freeipa_roster_file` entirely (present on
  `freeipa-server`/`nexus`, absent on `client-vm` in the round-31 template) — this made
  `freeipa-nfs-client-apply.yml`'s `Load canonical roster under a namespace` task fail
  outright (`'freeipa_roster_file' is undefined`), which — because it is a templating
  exception, not a normal per-host task failure — silently aborted the *entire* remaining
  `site.yml` multi-play chain (every later `import_playbook`, including `wazuh-manager`,
  `prometheus`, etc., never ran at all, even though the recap up to that point showed
  `failed=0`). Fixed by adding the same `freeipa_roster_file` value already used by the
  other two hosts.

None of these are pilot bugs — they are gaps in reusing a hand-copied workspace, listed
here because they cost real debugging time and are exactly the kind of "silently
plausible-looking but wrong" value a future re-run of this same scenario should
double-check up front (patch **every** host/group var that embeds another host's IP, not
just the obvious `ansible_host` fields).

## 4. Two real bugs in `internal/decommission/providers/freeipa_client.go`

**Root cause (both bugs share it):** `planner.go`'s `providerFQDN(host)` returns
`host.Name` — the workspace's own `hosts.yml` dict key — as this provider's "FQDN" input.
That is only actually an FQDN when a workspace author happens to key `hosts.yml` by FQDN
(the roster's own convention); a short key like `client-vm` (this workspace's, and
apparently `p6k-baremetal`'s own) is common and legitimate, but was silently assumed to
already be the real FreeIPA identity everywhere downstream.

1. **Ownership check always false-blocked.** `ipa host-show client-vm` (a short name)
   *succeeds* — FreeIPA completes it against the default domain — and returns the real
   host object, including its own `Principal name: host/client-vm.ipa.pilot.internal@...`
   line. But `unknownServicePrincipals`'s self-exclusion string was built from the
   *caller's* short input (`"host/" + "client-vm"`), which can never string-match the real
   `"host/client-vm.ipa.pilot.internal@REALM"` principal the query actually printed — so
   the host's own principal was always classified "unknown", hard-blocking every host
   whose `hosts.yml` key isn't already FQDN-shaped. **Fix:** derive the self-exclusion
   identity from the query result's own authoritative `Host name:` field
   (`resolveAuthoritativeFQDN`), falling back to the input only when that field is absent
   (host already gone).
2. **Roster mutation silently no-op'd.** Even after fixing (1), `pilot host decommission
   apply`/`resume` kept completing every step yet leaving the FreeIPA host
   object/hostgroup membership/DNS record present forever (correctly detected as
   `active_residue` by INV-10/11's independent re-verification — finalization correctly
   refused to complete on top of it, but the plan could never actually converge either).
   Root cause: `Plan()` built the `freeipa_roster_host_absent` step's `TargetIdentity`
   from the same short `fqdn` variable — but the canonical roster's `hosts[]` entries are
   always FQDN-keyed, so `RosterHostAbsentAndUnreferenced`/`SetRosterHostAbsent` silently
   matched nothing (`found=false`, treated as benign at Plan time) and never touched the
   real `client-vm.ipa.pilot.internal` roster entry. **Fix:** resolve the real FQDN via the
   same live query *before* the roster simulate/step-construction logic runs, and use that
   resolved value consistently for the roster-absent step, the roster simulate call, and
   the identity-apply-convergence step (which was already correct — it separately used
   `fqdn`, not `hostName`, and that's what first pointed at the inconsistency).

Confirmed via a live `-v`-instrumented run (temporary debug print, removed before
finishing) that `fqdn="client-vm"` was in fact reaching the roster step at runtime before
the fix, and the correct FQDN after. Both fixes are covered by new fixture regression
tests (`TestFreeIPAProvider_UnknownServicePrincipalBlocks/caller-supplied_FQDN_is_only_a_
short_inventory_name...`, `TestFreeIPAProvider_RosterAbsentStepTargetsFQDNNotHostName`) —
full suite (3369 tests) green after both fixes.

**A third, unrelated pre-existing bug** surfaced once the above cleared the way to
`wazuh-fim`'s own central deregistration step:
`playbooks/decommission/wazuh-manager-agent-deregister.yml`'s `manage_agents -r <id>` task
ran `set -o pipefail` without `args: {executable: /bin/bash}` — every *other*
`set -o pipefail` task in this codebase pairs the two; `/bin/sh` on Ubuntu is `dash`,
which doesn't support that option (`/bin/sh: 1: set: Illegal option -o pipefail`). Fixed
by adding the missing `executable: /bin/bash`.
