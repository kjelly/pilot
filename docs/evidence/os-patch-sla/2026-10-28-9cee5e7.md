# os-patch-sla-apply installs unattended-upgrades; `--check` no longer fails without it (2026-10-28)

Covers candidate `9cee5e7` on top of `main` `c99b9c4` (issue #167).

- `os-patch-sla-apply.yml` never installed `unattended-upgrades`. On a Debian/Ubuntu host without it, Step 4 (`systemd` start+enable) failed, both in a real apply and in `--check`.
- The candidate installs the package through `tasks/apt-package-install.yml` (strict policy, after Step 1's `update_cache`), skips the shared include under `--check`, gates Step 3, Step 4 and the restart handler on the package being usable, and fails closed after the install if the package is still absent. Spec row C8 (package installed) is added.

## Found, not fixed here

- **Step 3 has never run `unattended-upgrade`.** It passes `--non-interactive`, which Ubuntu 24.04's `unattended-upgrade` does not have: `unattended-upgrade: error: no such option: --non-interactive`, rc=2. `failed_when: false` hid this on `main`. The new Step 3b prints it on every real apply (a `debug`, not a failure). Fixing the flags changes behaviour: every apply would then really install security updates (including on `prod`), so it needs its own decision and test. It also means a fresh host never reaches C1/C2 = 0 through this playbook.
- **Spec row C1 cannot pass.** `apt list --upgradable 2>/dev/null | wc -l` counts the `Listing...` header line, so a fully patched host prints `1`, not `0`. Observed on the patched target before any playbook ran. Not changed here because relaxing an Expected value to make a run pass is out of this issue's scope.
- `vm-target test --spec docs/verification/os-patch-sla.md` cannot be used as-is on one VM, see the target table.
