# os-patch-sla-apply selects the group named by `patch_stage` (2026-10-29)

Covers candidate `2d70670` on top of `main` `d013ed9` (issue #177).

- `os-patch-sla-apply.yml` declared `target_group: sandbox` in its play `vars:`. Play vars shadowed the `hosts: "{{ target_group | default(patch_stage) }}"` default, so `-e patch_stage=staging|prod` (all that `pilot deploy` and `site.yml` pass) still selected the `sandbox` group. With no sandbox host the play printed `skipping: no hosts matched` and the run succeeded without patching anything; with sandbox hosts present the stage/environment-group gate failed the run.
- The candidate removes the play var, so the group is named by `patch_stage` unless `-e target_group=` is given. A new regression test runs `ansible-playbook --list-hosts` for every stage (direct, `site.yml`-style import, real `playbooks/site.yml`) and a repo-wide lint rejects any play var that shadows a `hosts:` default.

## Found, not fixed here

- **C1 fails on a fully patched host.** `apt list --upgradable 2>/dev/null | wc -l` prints `1` because of the `Listing...` header line, so the "= 0" row cannot pass. Same observation as the 2026-10-28 evidence; not related to target selection.
- **Applying never upgrades packages** (#172), so C1/C2 can only pass on a host that was patched beforehand, as these VMs were.
- **Rollout:** `staging` and `prod` hosts now run this playbook for the first time (install and enable `unattended-upgrades`, rewrite `/etc/apt/apt.conf.d/50unattended-upgrades`). Decide that together with #172.
- **Unknown stage:** `-e patch_stage=<typo>` now selects zero hosts and exits 0 instead of failing the `sandbox|staging|prod` assert (which stays reachable with an explicit `-e target_group=`). Covered by a regression test as intended behaviour; a zero-host warning in `site.yml` is a separate change.
