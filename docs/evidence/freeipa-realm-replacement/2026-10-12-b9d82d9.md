# FreeIPA realm replacement: rollback re-enrolls the client in the old realm — candidate `b9d82d9` (2026-10-12)

Scope: the run for `9a189be` ([evidence](2026-10-12-9a189be.md)) showed that the rescue restored the archive, but the old realm stayed offline. There were two causes:
- **The old host's keys were voided.** `ipa-client-install --uninstall` unenrolls the host with its own keys: `ipa-join --unenroll` calls `host_disable` on the old server. The archived keytab no longer worked there.
- **The archive misses most of the old configuration.** The uninstall also reverts authselect/PAM, the hostname, SSSD's and sshd's IPA settings, the CA trust and the installer's own state. SSSD is left disabled.

The candidate changes `freeipa-realm-replacement-apply.yml`:
1. **Before the uninstall:**
   - It records the old enrollment's domain, host and servers from `/etc/ipa/default.conf` and `sssd.conf`, and refuses to switch when any of them is missing.
   - It removes the old realm's keys from `/etc/krb5.keytab` with `ipa-rmkeytab`. The archive keeps them. The unenroll then cannot authenticate, the uninstall carries on, and the old host stays enabled on the old server.
2. **In the completion marker:** that host, as `old_host_still_enabled`.
3. **In the rescue, when the client is no longer enrolled in the old realm:**
   - It removes any new-realm enrollment and puts the old server pins back.
   - It re-enrolls with the archived keytab (`ipa-client-install --keytab`, with freeipa-client's options).
   - It restores the archive over that enrollment, except the keytab.

   If re-enrolling fails, it restores the whole archive and says that the old login path is not working. SSSD is enabled as well as restarted.

## Regression tests

`TestRegression_RealmReplacementRescueReenrollsTheOldRealm` runs the switch's preparation, key removal and uninstall, and then the rescue, on localhost. `ipa-client-install`, `ipa-rmkeytab` and `tar` are stubs that log their arguments. Four cases:

| Case | Expected commands |
|---|---|
| Failed before the uninstall | the archive is restored, nothing else |
| New realm enrolled | key removal; uninstall; the new enrollment removed; pins restored; keytab extracted to a private directory (gone afterwards); re-enrollment with the old domain, realm, host and both servers; the archive restored without the keytab |
| The enrollment rolled itself back | the same, without removing an enrollment |
| Re-enrollment fails | the whole archive restored, keytab included, and a message saying so |

Further tests:
- `TestRegression_RealmReplacementRefusesAnUnrestorableOldEnrollment`: a `default.conf` without `host` stops the switch.
- `TestRegression_RealmReplacementRemovesOldKeysBeforeTheUninstall`: locks the order.
- `TestRegression_RealmReplacementReenrollsLikeFreeipaClient`: the rescue's enrollment options equal `freeipa-client-apply.yml`'s, apart from `--force-join`.

Each of these changes to the playbook makes at least one test fail:
- no key removal;
- the rescue never re-enrolling;
- the keytab restored over the re-enrollment;
- `--no-ntp` dropped from the rescue;
- the new enrollment not removed;
- no restorability check;
- the extracted keytab left behind.

## Migration and the old host entry

After the wrong-password rollbacks, both clients were migrated again from that state:
- **The migration:** rc 0 (`changed=11`) and **`freeipa-realm-replacement.md` 6/6** on both. A client that was rolled back can therefore be migrated again.
- **The completion marker:** records `old_host_still_enabled=host/<host>.ipa.pilot.internal@IPA.PILOT.INTERNAL`.
- **The old server:** still shows `Keytab: True`.
- **A repeat:** refused by the completion-marker gate.
- **Retiring the old host entry:** `ipa host-disable c54-cl.ipa.pilot.internal` on the old server, as the old realm's admin, printed `Disabled host "c54-cl.ipa.pilot.internal"`. `ipa host-show` then showed `Keytab: False`. This is the step the runbook gives for retiring the old host entries once the wave is accepted.
