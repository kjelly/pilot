# FreeIPA realm replacement: single backslashes in the lineinfile regexes — candidate `4f2087a` (2026-10-12)

Scope: three regexes in `freeipa-realm-replacement-apply.yml` were written with doubled backslashes in single-quoted YAML, which keeps both:
- **"pin SSSD to the new server", `insertafter: '^\\[domain/'`.** Python compiled a literal backslash and then a `[` that never closes. Every migration failed there with "unterminated character set at position 3", right after the client had enrolled in the new realm, and the rescue restored the old realm.
- **Its `regexp: '^ipa_server\\s*='`, and "pin new server FQDN"'s `regexp: '\\s<fqdn>(\\s|$)'`.** These never matched, so `lineinfile` appended a line instead of replacing the existing one.

The candidate writes one backslash in each and adds `TestRegression_RegexArgsUseSingleBackslashes`. That lint covers `lineinfile`/`replace` `regexp`, `insertafter`, `insertbefore`, `after` and `before` across `playbooks/**`. A scan found no other case.

## Why the Ubuntu client still fails (found here, not changed)

The cause of the C5 failure recorded on 2026-07-29 was found here. To keep the state after the enrollment, the migration was run on the Ubuntu client with `--skip-tags C5`:
- SSSD for `new.example.test` stayed **Offline**.
- `ldap_child.log` repeated "Client 'host/c52-cl.new.example.test@NEW.EXAMPLE.TEST' not found in Kerberos database".
- `sssd_new.example.test.log` showed "Could not get TGT … 14 [Bad address]" and "Server [NULL] resolution failed".
- A root `kinit -k` (with and without `-C`) for the same principal succeeded against the new KDC.
- The KDC logs show why: SSSD's AS requests for the new principal went to the **old** server (`ipa1.ipa.pilot.internal`'s `krb5kdc.log`); root's went to the new one.

`/etc/hosts` still held the old realm's server pin from `freeipa-client-apply.yml`, `<old-ip> ipa1.ipa.pilot.internal ipa1`, next to the new `<new-ip> ipa1.new.example.test ipa1`. `ipa-client-install --uninstall` does not remove that pin, and both lines carry the short name `ipa1`. Removing the old line and restarting SSSD brought the domain Online within 15 seconds, and `getent passwd admin@new.example.test` resolved.

On the AlmaLinux client the same stale line was present, but SSSD was Online with or without it.

A fix belongs in the realm replacement: drop the old realm's server pins before enrolling. It needs its own Ubuntu run.

## Other findings, not changed

- **`--check --diff` of the migration always fails.** It fails at "expose archive through a stable root-only link": no archive exists under `--check`, so the link's source is missing. The rescue then prints "The prior local client configuration was restored", although nothing ran.
- **The archive name can be stale.** It uses `ansible_date_time`. With the repository's `gathering = smart` and a one-hour fact cache, a repeat within the hour reuses the same archive name and `tar -czf` overwrites the earlier archive.
