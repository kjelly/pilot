## Change

- **Archive name.** A task at the start of `tasks:` (tag `always`) names the archive once per run from the controller's UTC clock: `<inventory_hostname>-<YYYYmmddTHHMMSSZ>.tar.gz` under the same directory. The snapshot, the rescue, the completion marker and the link read that fact. The play variable that built the name from `ansible_date_time` is gone.
- **No overwrite.** Before the snapshot, a gate refuses when an archive of this run's name already exists (an `-e` override, or two runs within one second); nothing is changed.
- **Check mode.**
  - The link takes `force` only in check mode. Check mode skips the snapshot, so the link's source did not exist; a real run still refuses a missing archive.
  - The read-only "client must still be enrolled in the declared old realm" gate gets `check_mode: false`. Check mode used to skip this shell task.

### The new server's host entry after a rollback (not changed)

A verification user that does not exist makes the identity wait (C5) fail after the new enrollment completed; the rescue then uninstalls the new enrollment and re-enrolls the old realm. Each run started from `ready`; two ran at the same time on different clients and servers.

| Client, new server | Host entry before | Rescue's uninstall | Host entry after | Client after |
|---|---|---|---|---|
| Ubuntu, `p56-new2` (own FQDN), run 1 | none | `Unenrolling host failed: cannot connect to 'ldapi://%2Frun%2Fslapd-NEW-EXAMPLE-TEST.socket'`, then `Client uninstall complete` | **enabled, `Keytab: True`**; the client no longer holds those keys | login ok, **12/12**; old server `Keytab: True` |
| Ubuntu, `p56-new2`, run 2 (same case again) | none | `Unenrollment successful` | `Keytab: False` | — |
| Ubuntu, `p56-new` (shared FQDN) | none | `Unenrollment successful` | `Keytab: False` | login ok, **12/12** |
| AlmaLinux, `p56-new2` | none | `Unenrollment successful` | `Keytab: False` | login ok, **12/12** |
| AlmaLinux, `p56-new`, entry **added by the operator beforehand** (`ipa host-add --force`, with a description) | `Keytab: False`, description set | `Unenrollment successful` | `Keytab: False`, description kept | login ok, **12/12** |

With a wrong password the new enrollment never joins, and no entry is left (all four wrong-password rollbacks above).

The migration was then run again from the first two rows' state:
- Ubuntu, with the enabled leftover entry on `p56-new2`: rc 0, **6/6**, `Keytab: True`.
- AlmaLinux, with the operator's disabled entry on `p56-new`: rc 0, **6/6**, `Keytab: True`, the description kept.

What this shows:
- The entry is left by every rollback that follows a completed new enrollment, with either FQDN and on both platforms, not only when the FQDN is shared.
- Usually the uninstall's unenroll disables it, which matches an entry the operator added beforehand. Once in two identical Ubuntu runs the unenroll failed (above) and the uninstall still completed, so the entry stayed enabled with keys no machine holds. The cause of that failure was not found.
- Neither state stopped a later migration of the same client: `--force-join` and the admin principal re-key the entry.
- An entry the operator added beforehand (runbook §1 asks for host records on the new server before the wave) keeps its data through the rollback. Deleting entries in the rescue would remove those; the rescue cannot tell them apart from entries the enrollment created.

So this change leaves the entry alone. The runbook's rollback boundary (§3) says what is left and how to clean it up when a wave is abandoned.
