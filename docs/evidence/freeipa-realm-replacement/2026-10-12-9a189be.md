# FreeIPA realm replacement: drop the old realm's server pins before enrolling — candidate `9a189be` (2026-10-12)

Scope: on Ubuntu 24.04 every migration failed at the identity wait (C5). The cause was found in the run for `4f2087a` ([evidence](2026-10-12-4f2087a.md)):
- `freeipa-client-apply.yml` pins the old realm's server in `/etc/hosts`, `<old-ip> ipa1.ipa.pilot.internal ipa1`.
- `ipa-client-install --uninstall` does not remove that line, and it carries the same short name `ipa1` as the new pin.
- SSSD sent the new host principal's AS requests to the old KDC and stayed Offline.

The candidate adds four tasks to the destructive block of `freeipa-realm-replacement-apply.yml`:
1. Before the uninstall, read `/etc/ipa/default.conf` and `/etc/sssd/sssd.conf`.
2. List the old realm's servers from them: `server`, `ipa_server` and `ipa_backup_server`, without `_srv_` and without the new server's FQDN.
3. After the uninstall and before the new enrollment, remove the `PILOT FREEIPA SERVER POOL` block from `/etc/hosts`.
4. Then remove any other line that names one of those servers, matched case-insensitively. This covers pins written by older clients without a marker.

The rescue's archive still restores `/etc/hosts` when the enrollment fails.

## Regression tests

`TestRegression_RealmReplacementRemovesOldServerPins` runs the four tasks on localhost against a temporary `default.conf`, `sssd.conf` and `hosts`, each case twice:
- Pilot's pool block is removed; the new server's pin and the client's own line stay.
- Unmarked pins from an `ipa_server`/`ipa_backup_server` failover list are removed, in any case.
- A new server that keeps the old server's name keeps its line.
- The second run changes nothing.

`TestRegression_RealmReplacementRemovesOldPinsBetweenUninstallAndEnroll` locks the order inside the destructive block: read, list, uninstall, pool block, other pins, enroll.

Each of these changes to the playbook makes the first test fail:
- an empty loop for the unmarked pins;
- `ipa_backup_server` dropped from the regex;
- the new server's FQDN not excluded from the list;
- a different block marker.

`TestRegression_FreeIPARealmReplacementContract` used to fail on any `state: absent` in the playbook. It now fails only when a `file` task with `state: absent` targets the backup archive; a task that deletes the archive still makes it fail.

## Other findings, not changed

- **The rescue restores the files, not working access, even while the old server runs.** After the failed-enrollment run above, `getent passwd admin@ipa.pilot.internal` returned rc 2, and SSSD stayed Offline for the old domain. `ldap_child.log` showed "Generic preauthentication failure" for the restored keytab. The old server's `httpd` log shows why: during `ipa-client-install --uninstall` the client called `host_disable` for its own host entry, which removes the host's keys on the old server. The control showed the same rc 2 after its rescue, so this is not caused by the candidate. The runbook's rollback boundary now states it; the rescue's message ("only restores working access if the old FreeIPA server and its client principal still exist") is still misleading and is left for a separate change.
- **`--check --diff` of the migration always fails**, at "expose archive through a stable root-only link", on both revisions; the rescue then prints that it restored.
- **The archive name can be stale.** Every run on the Ubuntu client, up to 15 minutes after the first, used the same archive name `c53-cl-20261012T130927`, because `ansible_date_time` comes from the one-hour fact cache. A repeat on a host that was not reverted would overwrite the earlier archive.
