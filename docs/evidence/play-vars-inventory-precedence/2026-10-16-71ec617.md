# log-server PR #79 on candidate `71ec617` (2026-10-16)

This record replaces `2026-10-16-56c7582.md` as the current record for PR #79.

**What changed since `56c7582`.** The `56c7582` run found that changing `siem_log_root` on Ubuntu lost messages. Step 2a wrote only the new root's rules into the AppArmor block and reloaded the profile before Step 6a restarted rsyslog. ## The fix

On Ubuntu, for a root outside `/var/log`:

1. **Step 2a, phase `grant`**, before rsyslog restarts. It reads the rules between the pilot markers in `/etc/apparmor.d/local/usr.sbin.rsyslogd` and keeps them, adding the new root's rules. For an unchanged root the block is unchanged. It then reloads the profile by its loaded sha256, as before.
2. **Step 6a** restarts rsyslog as before. It also restarts rsyslog when rsyslog started before the receiver config was last written: a run interrupted before Step 6a, or a rescue that put a config back and could not restart.
3. **Step 7** checks three things: rsyslog is active, it started after the receiver config was last written, and an `rsyslogd` process listens on the receiver port. It retries for up to 10 s. The run fails when rsyslog is inactive or not listening.
4. **Step 7a, phase `narrow`**, runs only when Step 7's check printed `ok`. It writes only the new root's rules, or removes the block for a root under `/var/log`, and reloads only if the block changed. It carries every row tag and checks Step 7's result itself, so under `--tags` it runs only after the same check (AGENTS §4.4).
5. **The rescue** leaves the AppArmor local file out of its first restore.
   - It reads the local file as the failed run left it, writes the union of the rules from before the run and from the run, and reloads. The running rsyslog can then write whichever root it uses.
   - After validating and possibly restarting, it puts back the local file from before the run only when rsyslog runs a configuration those rules cover: the rescue restarted it, or its `InvocationID` is the one the snapshot read. Otherwise it keeps the union, and the message says so. The next successful run restarts rsyslog (Step 6a) and drops the extra rules (Step 7a).
   - While rsyslog still runs the configuration from before the run, the put-back receiver config also gets its modification time back, so the next run does not restart rsyslog for it.

**SELinux is unchanged.** On EL the file-context rule for an earlier root stays, by design: no step of this PR ever removes one, except the rescue removing a rule its own failed run added. The SELinux tasks run in the grant phase only. The rescue reads `rsyslog_selinux_fcontext_added`, which the narrow phase does not overwrite. This run left the rules for `/srv/siem-el`, `/srv/siem.el2`, `/srv/siem.elS1` and `/srv/siem.elS3` on `pr79-el`.

**The old root comes from the local file**, the rules the profile grants after the last reload, not from inventory. A rule loaded but no longer in the file (the file edited without a reload) is not kept.

### Message streams during a root change

Each stream run applies log-server with a new root while `pr79-client` sends two numbered streams, 300 messages each at one per 0.1 s, starting 5–7 s before the run:

- **hosts** (`pr79h.py`): `local6.info` messages straight to the receiver's tcp/514, each over a new TCP connection. The syslog HOSTNAME cycles through 20 names, more than rsyslog's dynafile cache (10 files), so most messages make the receiver open a file. A send the receiver refuses (connection refused during a restart) is counted as not sent.
- **fwd** (`pr79s.sh`): `logger -p local6.info` on `pr79-client`, through its own rsyslog and the audit-log-forwarding rule to `siem-log-server:514`.

**Received** counts the stream's numbers found under `/srv` and `/var/log/siem` on the receiver after the run. **Denied** counts the receiver's rsyslog journal lines with `Permission denied` from the start of the streams. Each failed run fails on purpose; the failure is described in the row:

- **after the reload, before the restart**: an invalid drop-in (`this is not rsyslog syntax {`), written before the run, fails Step 5 (`rsyslogd -N1`), after Step 2a's reload and before Step 6a's restart; the rescue cannot restart rsyslog.
- **after the restart**: `-e '{"log_server_receiver_state": {"stdout": "not-listening"}}'` overrides Step 7's register (extra vars take precedence), so Step 7 fails after Step 6a restarted rsyslog on the new root. In "rescue cannot restart", `plant-after-restart.sh`, started on the receiver before the run, waits until rsyslog's `InvocationID` changes and then writes the same invalid drop-in, so the rescue's validation fails.

Between runs, the same playbook was applied with the base root and no stream; 35 s passed before each stream.
