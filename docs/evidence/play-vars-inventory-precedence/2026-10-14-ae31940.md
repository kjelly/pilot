# SIEM playbooks read every input their specs list — candidate `ae31940` (2026-10-14)

> Superseded for PR #79 by [`2026-10-15-d545868.md`](2026-10-15-d545868.md). This run used an earlier candidate and does not record run-time metadata; it is not evidence for the current candidate.

Follows `2026-10-14-d0d369e.md`. The review of PR #79 at `48138ef` found:

- **The receiver port was still shadowed.** log-server declared `siem_receiver_tcp_port` in its play vars, although `docs/verification/log-server.md` §1.5 lists it as an input. The play-vars lint counted only contract `groupVars` and example keys as inputs, so it did not see this variable. With `siem_forward_port` and `siem_receiver_tcp_port` both set to `2514`, the clients sent to 2514 and rsyslog listened on 514. The apply succeeded.
- **Empty or null `siem_log_root` split the two sides.** log-server took `""`, while log-shipping fell back to `/var/log/siem`.
- **`siem_log_root` could name a shared system directory.** log-server would take over `/var/log` and rotate its logs.

`ae31940` makes these changes:

- **Playbooks.** log-server, audit-log-forwarding and log-shipping now default every variable their spec's §1.5 lists in an always-tagged `set_fact`.
- **Contracts.** The four SIEM contracts declare those variables in `groupVars`.
- **Empty or null values.** `siem_log_root` and the SIEM ports fall back to their defaults on every side, wazuh-manager included.
- **Gate.** log-server refuses a `siem_log_root` that is not a dedicated absolute directory.

After the `siem_log_root: ""` run, the first message was lost, and a second message 30 s later arrived. The client's journal explains the loss. When the apply restarted rsyslog on both hosts, the client's forwarder got "Connection refused" and suspended itself for 30 s. rsyslog drops messages while the forwarder is suspended. This applies to every audit-log-forwarding apply that restarts rsyslog, and is not changed here.
