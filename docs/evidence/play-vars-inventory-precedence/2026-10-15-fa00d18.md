# SIEM probes on the effective log root, confined rsyslogd — candidate `fa00d18` (2026-10-15)

> Superseded for PR #79 by [`2026-10-16-56c7582.md`](2026-10-16-56c7582.md): a review of `fa00d18` found three problems in its log-root access step (Step 2's tags, the SELinux relabel condition, unchecked characters in the resolved root).

This record follows `2026-10-14-4115817.md`. The review of PR #79 at `e0b319c` found two problems:

- **[P2] Acceptance still checked the default log root.** `siem_log_root` from inventory takes effect, but `log-server.md` C6–C8 were fixed to `/var/log/siem`.
  - With a custom root, C6–C8 failed on a fresh host.
  - An old fixed `PILOT-SIEM-SELFTEST-*` string left in `/var/log/siem` could make C7/C8 pass.
- **[P3] Committed VM summaries lacked fields required by `docs/actual-run-evidence.md` §3:** the target image digest, run ID, UTC window and inventory fingerprint.

The VM run of the first fix, candidate `8820b04`, found a third problem: **rsyslogd could not write a non-default root at all.**

- Ubuntu 24.04 confines rsyslogd with the AppArmor profile `usr.sbin.rsyslogd`, which allows writes under `/var/log` only.
- With `siem_log_root: /srv/siem`, rsyslog logged `omfile: creating parent directories for file '/srv/siem/pr79-log/audit.log' failed: Permission denied` and discarded every message, while the apply succeeded.
- Promtail's `/ready` then answered 500 (no file to tail), so the `8820b04` topology test failed at L4 and rolled back.
- On EL, SELinux lets `syslogd_t` write only `var_log_t` files, and a directory created under `/srv` is labelled `var_t`.
