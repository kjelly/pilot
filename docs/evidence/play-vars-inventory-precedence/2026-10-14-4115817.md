# SIEM log root: Step 2 on the resolved path — candidate `4115817` (2026-10-14)

> Superseded for PR #79 by [`2026-10-16-032a8b3.md`](2026-10-16-032a8b3.md). This run used an earlier log-server playbook and `pilot` binary and does not record the target image digest, run IDs, operator or input fingerprints; it is not evidence for the current candidate.

This record follows `2026-10-14-1d9bd8c.md`. A fourth review of PR #79 at `36c2c46` found no P1 or P2. Its P3 findings changed these things:

- **Step 2 and symlinks.** The gates checked the directory `siem_log_root` resolves to. Step 2, however, made the *written* path owned by the rsyslog user and followed a symlink. On Ubuntu that user may write `/var/log`, so between the gates and Step 2 it could swap the directory for a symlink and get the target chowned. Step 2 now works on `siem_log_root_real` with `follow: false`.
- **Trailing newline.** The name gate ended in `$`, which let a trailing newline through. It now ends in `\Z`.
- **Missing passwd entry.** The dedicated-directory assertion now defaults `pw_name` and `gr_name`, which are absent for a uid with no passwd entry.
- **Comments.** They now say that:
  - an unquoted `02514` or `0x9C4` in YAML reaches Ansible as 1356 or 2500;
  - the FQDN match needs the log-server's facts in the run;
  - the mount-point rule also accepts an empty bind mount or subvolume.
- **C22.** It now retries for up to 8 s, down from 10 s, leaving room in the 15 s row timeout (`audit-log-forwarding.md` v1.8).
- **The `1d9bd8c` record named the wrong failing test** for the validate change. That row is corrected.
