## Real findings this round

### 1. Playbook bug (fixed): `freeipa-identity-apply.yml`'s top-level-key gate rejected `domain`/`realm`

First `pilot reconcile` attempt for `freeipa-identity` failed at "Gate: canonical top-level and
FreeIPA keys are known":

```
Canonical roster contains an unknown freeipa/admin field.
"assertion": "((freeipa_roster.freeipa | default({})).keys() | list | difference(['server', 'admin', 'defaults', 'safety'])) | length == 0",
```

The roster's `freeipa.domain` key (written automatically by `pilot edit`'s NFS-role-add
bootstrap, `internal/inventory/nfs_bootstrap.go`'s `WriteMinimalNFSServerRoster`) was rejected —
even though `internal/inventory/roster_validate.go`'s `knownFreeIPAKeys` explicitly permits
`domain`/`realm`, with a comment stating the apply playbook is supposed to just ignore them, not
reject them. This means **any** workspace built through the sanctioned NFS-role-add path fails
`freeipa-identity` reconcile on the very first gate — `pilot roster lint` never catches it since
the Go-side validator already allows the shape. Fixed by adding `domain`/`realm` to the assert's
allowed `freeipa.*` key list, matching the Go-side schema exactly. Re-ran after the fix: preview
and real apply both passed (`changed=20 failed=0`).

### 2. Playbook bug (fixed): `freeipa-dns-apply.yml`'s `ipa_server_fqdn_expected` used the wrong default

First `pilot reconcile` attempt for `freeipa-dns` (after authoring a manifest live via `pilot
edit`'s new manifest menu) failed at "Gate: manifest freeipa.{domain,realm,server} match this
inventory":

```
manifest freeipa.domain/realm/server must equal this deployment's freeipa_domain/freeipa_realm/freeipa_server_fqdn (§5.2) —
got ipa.pilot.internal/IPA.PILOT.INTERNAL/ipa1.ipa.pilot.internal vs ipa.pilot.internal/IPA.PILOT.INTERNAL/freeipa-server.
```

The expected side (`freeipa-server`, the inventory's bare host alias) came from
`ipa_server_fqdn_expected: freeipa_server_fqdn | default(inventory_hostname)` — falling back to
`inventory_hostname` when `freeipa_server_fqdn` was left unset, exactly the case
`group_vars/freeipa.example.yml`'s own comment recommends ("通常不用填"). This doesn't match the
FQDN `freeipa-server-apply.yml` itself computes and actually installs the server as
(`'ipa1.' ~ ipa_domain`, i.e. `ipa1.ipa.pilot.internal`). Every `freeipa-dns` reconcile against a
workspace following the documented convention hit this. Fixed by changing the default to
`'ipa1.' ~ ipa_domain`, matching `freeipa-server-apply.yml` exactly. Re-ran after the fix: preview
and real apply both passed (`changed=2 failed=0`).

### 3. New capability confirmed: the roster manager now covers per-entry fields and membership

Contrary to this repo's own prior memory/documentation ("roster manager only supports append-only
Users/Groups creation"), the current build's roster manager (`cmd/pilot/cmd/edit_tui_roster_*.go`)
covers full per-user field editing (password, `enabled`, shell, home directory), per-group
membership checklists, and a "Host access"/"Sudo commands & rules" screen for *group→hostgroup*
HBAC/sudo rules. It does **not** cover `hostcat: all`-style rules (e.g. a breakglass admin rule) —
attempting one through the wizard correctly fails closed with no partial write ("HBAC rule ...
needs at least one subject user or group" / "targets must be hostcat: all, or list
hosts/hostgroups"), confirmed live. The breakglass rule and the NFS share were still hand-edited
into the roster's nested YAML this round for that reason — a narrower exception than previously
documented, not eliminated.
