## Real findings this round

### 1. Script bug (fixed): `host_vars` field pre-fill + `TEXT_AND_ENTER` doubled `prometheus_site_label`

The leftover round-17-attempt workspace's `host_vars/nexus.yml` already showed
`prometheus_site_label: site-nexussite-nexus` before this round even started scripting anything —
direct, real evidence of the documented "text fields pre-fill with the cursor at the end; plain
`TEXT` appends instead of replacing" gotcha (`pilot-trec-verification` skill §4) actually firing
against this exact script. `01-edit-hosts.drive`'s line setting this field used
`TEXT_AND_ENTER site-nexus` — safe only if the field is guaranteed blank, which it is not across a
retried run in the same workspace. **Fixed**: changed to `REPLACE_TEXT_AND_ENTER` (sends Ctrl-U
first). Applied the same hardening to every other value-set field in the script
(`ansible_host`/`ansible_user`/SSH-key-path × 3 hosts, and the `group_vars` value edits in the new
`01b-edit-group-vars.drive`) as defense-in-depth — harmless on an already-blank field, and prevents
this exact failure mode on any future re-run of a partially-built workspace.

### 2. Script bug (fixed): `host_vars` save returns one menu level higher than the script assumed

First unattended run of the hardened script still failed, at `EXPECT 選一台主機，或選下面的操作`
right after saving `host_vars/nexus.yml`. The transcript showed the save actually returns to the
**host's own item menu** (`主機 "nexus" — 選要編輯的項目`), not the top-level host list — consistent
with every other sub-editor in `pilot edit`'s nested menu structure, just not what the script (newly
authored for this feature in round 16) assumed. **Fixed**: added the missing
`EXPECT 選要編輯的項目` / `CHOOSE ↩ 返回主機清單` step, matching the pattern already used correctly
elsewhere in the same script for the analogous freeipa-server/client-vm transitions.

### 3. Script bug (fixed): roster manager's Users screen "↩ 返回" also returns one level higher than assumed

Second unattended run got to the very last step before failing: after adding both roster users,
`CHOOSE ↩  返回` (from the Users screen) lands on the roster's own `管理 <roster>` submenu
(`👤 Users` / `👥 Groups` / `↩ 返回`), not the top-level `要編輯什麼？` menu — the **Groups** exit
earlier in the same script already had the correct two-step pattern; the **Users** exit was missing
the equivalent second `↩ 返回`. **Fixed**: added the missing `EXPECT 管理` / `CHOOSE ↩ 返回` pair.

With all three fixes applied, `01-edit-hosts.drive` completed unattended end to end
(`process exited 0`) on the next attempt, and every checked-in script in the suite now has at least
one fully unattended, successful run backing it — the `README.md` caveat this round set out to
close.

### 4. Suspected implementation defect (reported, not fixed; worked around in the roster): `freeipa-identity-apply.yml` crashes when the canonical roster omits the optional `freeipa.server` field

`pilot reconcile`'s preview crashed with:

```
Error while resolving value for 'identity_hbac_test_host': object of type 'dict' has no attribute 'server'
```

Root cause, read directly from `playbooks/apply/freeipa-identity-apply.yml`'s "Normalize canonical
FreeIPA settings" task (~line 289-299): every sibling field in the same `set_fact` block has a
`| default(...)` fallback —

```yaml
ipa_domain: "{{ freeipa_roster.freeipa.domain | default('ipa.pilot.internal') }}"
ipa_realm: "{{ freeipa_roster.freeipa.realm | default(freeipa_roster.freeipa.domain | default('ipa.pilot.internal') | upper) }}"
identity_admin_principal: "{{ freeipa_roster.freeipa.admin.principal | default('admin') }}"
identity_admin_password: "{{ freeipa_roster.freeipa.admin.password }}"
identity_hbac_test_host: "{{ freeipa_roster.freeipa.server }}"
```

— except `identity_hbac_test_host`, which reads `freeipa_roster.freeipa.server` with no fallback at
all, even though the same playbook already establishes a sensible top-level default for exactly this
variable at line 70 (`identity_hbac_test_host: "{{ ipa_server_fqdn | default(inventory_hostname) }}"`)
for the non-canonical-roster code path. Cross-checked three ways before reporting:

1. **Roster shape is legitimate, not an authoring mistake.** `internal/inventory/nfs_bootstrap.go`'s
   `WriteMinimalNFSServerRoster` — the function `pilot edit`'s own NFS-role-add bootstrap calls —
   writes only `schema_version`, `freeipa.domain`, and `freeipa.admin.{principal,password}`. It
   never writes `freeipa.server` or `freeipa.realm`. This is the exact roster shape this round's
   `01-edit-hosts.drive` produces, unattended, through a fully sanctioned tool feature.
2. **Not required by any validator.** `internal/inventory/roster_validate.go`'s `knownFreeIPAKeys`
   lists `server` as a *legal* key, not a *required* one; `./pilot roster lint` reported "ok: no
   issues found" against a roster missing it. `contracts/freeipa-identity.yaml` only declares
   `ipa_admin_password` as required input — nothing about `freeipa.server`.
3. **Reproduction changed exactly one variable.** Adding `freeipa.server: ipa1.ipa.pilot.internal`
   (the freeipa-server host's real FQDN, confirmed live via `hostname -f` on the VM — not guessed)
   to the roster, with nothing else changed, made the identical preview complete cleanly.

**Not fixed in code this round** — per the workflow's stop-condition rule, no Ansible/Go change was
made without the user's authorization. Worked around at the roster-content level only (adding
`freeipa.server`/`freeipa.realm` to this round's `.vault/ipa-identity.yaml`, which is squarely
within the already-sanctioned hand-edit exception for roster nested YAML, not an implementation
change). Reported to the user with the proposed direction: give `identity_hbac_test_host` the same
`| default(ipa_server_fqdn | default(inventory_hostname))` fallback its sibling top-level default
already uses, so a roster that legitimately omits the optional `server` field doesn't crash the
reconciler — mirroring the exact shape of the two similar defects round 16 found and fixed
(`ipa_dm_password` wrongly required; a missing-field crash in the same playbook's user-normalization
task).

## Evidence integrity

15 casts were produced and kept this round (14 individual steps + 1 merged full-walkthrough, via
`trec merge --gap 2`), all passing `trec verify`/`trec scan` in a single batch pass: `complete:
true`, `session_end_final: true`, `exit_code: 0`, `findings_count: 0`, `safe_to_share: true` for
every one (each also carries the expected `recording was produced by a dirty trec build` warning —
the local `trec` binary itself, unrelated to the `pilot` candidate). Self-contained HTML players
were generated for all 15 (`casts/html/*.html`) for direct teaching use.

**One cast was produced, found unsafe, and discarded rather than kept**: the first attempt at
`02-edit-vault-secrets.cast` scanned positive for 2 unredacted secrets. Root cause: the vault
editor's key-list screen re-renders **every already-set key's value** in plaintext each time it
opens — including `ipa_admin_password`, which this script doesn't set but which was already sitting
in `.vault/main.yaml` from the earlier NFS-bootstrap step — and that key hadn't been declared via
`--secret-env` for *this* script's own invocation. Fixed by declaring `--secret-env IPA_ADMIN_PW`
alongside the keys the script actually sets, and by resetting the vault file's other 7 keys (via the
wizard's own `刪除` action, not a hand-edit) back to unset before re-recording, so the re-run
exercises the intended "add fresh key" flow rather than "edit an existing key." The discarded cast's
`.result.json` sidecar was deleted alongside it. No secret value from the discarded cast was
committed, published, or reused; all values involved are disposable test credentials for this local
sandbox topology.

No `trec mcp` sessions were left open (each exploratory session in this round was explicitly closed
after use); `session_list` was not needed to audit for leaks since every session was tracked and
closed inline.
