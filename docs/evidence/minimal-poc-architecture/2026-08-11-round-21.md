## Real finding this round (fixed, user-authorized)

### `freeipa-nfs-server-apply.yml` never updated for Roster Schema v2 — hardcoded `schema_version == 1`

The site-wide deploy's `--check --diff` preview failed on `nexus` at task "Gate: required roster and
stage authorization" (`playbooks/apply/freeipa-nfs-server-apply.yml:33`), which asserted
`freeipa_roster.schema_version | int == 1`. This playbook independently loads the same canonical
roster (via the `freeipa_roster_file` host var, set on `nexus` per this runbook's §2) to resolve its
own NFS server/share entries — and was evidently never updated when the rest of the Roster Schema v2
rollout (Go validator, `freeipa-identity-apply.yml`, migration tooling, docs) happened. The roster
itself was not at fault: it lints clean (`pilot roster lint` → `ok: schema v2; no issues found`) and
follows the canonical v2 example's own conventions.

Confirmed by cross-referencing the sibling playbook's own already-correct check:
`freeipa-identity-apply.yml:137` uses `freeipa_roster.schema_version | int in [1, 2]`. Fix (applied
after explicit user authorization, since it is a playbook change): changed line 33 to the identical
`in [1, 2]` form. `ansible-playbook --syntax-check` clean; `go build`/`go test ./...` still
1626/1626 passing (no existing test referenced this exact assert). Re-running the full deploy
preview+apply afterward confirmed the fix resolved the block with no other regressions.

This was the **only** implementation defect found this round — everything else (the roster's own
structure, the wizard-driven workspace build, the reconcile's remove/restore/drift/idempotency
behavior) worked correctly on the first real attempt against the actual v2 implementation.

## Environment-pollution note (not a pilot defect, but worth recording)

`pilot deploy`'s completeness gate initially failed on an unrelated cause: a stray, pre-existing
`host_vars/nexus.yml` at the **repo root** (not this round's workspace), left over from some earlier
`pilot edit`/`pilot inventory generate` invocation run without `--dir`. Because `internal/ansible`'s
`Runner.Run` never sets `cmd.Dir`, `ansible-playbook` inherits pilot's own process working directory,
and Ansible's vars-plugin search path includes cwd-adjacent `group_vars`/`host_vars` in addition to
the inventory- and playbook-adjacent ones — so the repo-root skeleton's empty
`prometheus_site_label: ""` silently won over the workspace's correctly-filled value. A safe
read-only check (`ansible -m debug -a "var=thanos_s3_target_host"`) confirmed the same mechanism
would have also shadowed `group_vars/prometheus.yml` for the same reason, which could have
misconfigured (not just blocked) the real deploy.

Repo root also turned out to have a real `.vault/main.yaml` and two more `group_vars/*.yml` files
predating this session (gitignored, so invisible to a normal `git status`) — plausibly belonging to
a separate, unrelated `pilot edit`/`inventory generate` invocation run directly against the repo
root at some earlier point. These were left untouched (not moved, not read) since their ownership
was ambiguous. The round's own deploy was unblocked instead by constructing an isolated working
directory (`tmp/minimal-poc-20260811-round21/run-cwd/`) — symlinks to every repo-root top-level entry
**except** `group_vars`/`host_vars`/`.vault`/`tmp` — and running `pilot deploy`/`pilot reconcile`
with that as cwd. Verified via the same read-only `ansible -m debug` check that both
`thanos_s3_target_host` and `prometheus_site_label` resolved correctly from there. Fully additive
and reversible; nothing in the real repo root was modified by this workaround.

This is a real, general cwd-sensitivity gap in `pilot deploy`/`pilot reconcile`'s design (any
repo-root pollution can shadow any workspace's own group_vars/host_vars), not specific to this
round or to Roster Schema v2 — worth a future Go-side fix (`cmd.Dir` should probably be pinned to
the repo root explicitly, independent of the invoking process's own cwd), but that fix is out of
this round's authorized scope.

## First-ever proof: v2 netgroup membership removal and restoration

Every prior round's roster testing (and the background review agent's own read of the test suite
before this round) confirmed netgroup *creation* and *attachment* worked, but no round had ever
exercised removing a netgroup's membership and confirming the removal actually took effect on a live
FreeIPA server, nor restoring it afterward. This round did both, live:

- Removal: roster edit set `ng-nfs-clients.membership.hostgroups: []`; reconcile logged `changed:
  [freeipa-server] => (item=sysops-hosts -/-> ng-nfs-clients)`; `ipa netgroup-show ng-nfs-clients
  --all` afterward showed no `Member Hostgroup` line at all.
- Restoration: roster edit restored `hostgroups: [sysops-hosts]`; reconcile logged `changed:
  [freeipa-server] => (item=sysops-hosts -> ng-nfs-clients)`; `ipa netgroup-show` afterward showed
  `Member Hostgroup: sysops-hosts` again.
