## Real bugs found and fixed this round (all with explicit user authorization before touching code)

1. **`freeipa-nfs-client-apply.yml`'s new fail-closed gate was not check-mode-safe.** A fresh,
   not-yet-enrolled host's `hostname --fqdn` only reports its real FQDN after `ipa-client-install`
   actually runs (a real mutation, never during `--check`), so the gate failed the very first
   site-wide preview. Fixed by adding `when: not ansible_check_mode` to the gate assert and to the
   "use first matching entry" `set_fact`, mirroring `freeipa-nfs-server-apply.yml`'s own identical
   pattern (`Gate: inventory FQDN maps to exactly one safe NFS server`) — a pattern I should have
   copied the first time.
2. **The mount-verify task's hard failure cascaded through the rest of `site.yml` for that host.**
   Ansible's default behavior excludes a host from every subsequent play once it fails a task in
   the current run. The mount-verify check's own prerequisites (the IPA automount map/key, created
   only by the separate `freeipa-identity` day-2 reconcile; the NFS server FQDN actually resolving,
   which needs the separate `freeipa-dns-client` day-2 role) are never guaranteed to exist during a
   plain `site.yml` pass, since both run *after* `site.yml` in this project's own established
   rebuild order. Without a fix, the very first real apply this round silently skipped
   `host-monitoring`/`wazuh-fim`/`restic-backup`/`audit-log-forwarding` on `client-vm` entirely.
   Fixed with `ignore_errors: true` on that one task — the real pass/fail result stays visible in
   the recap as `ignored`, but no longer blocks the rest of the host's roles.
3. **`contracts/freeipa-ca-trust.yaml` declared `role: freeipa-ca-trust`, but the component
   actually targets the literal `all` inventory group by design** (`freeipa-ca-trust-apply.yml`'s
   own `hosts: "{{ target_group | default('all') }}"`). `cmd/pilot/cmd/deploy.go`'s dependency
   resolver resolves a component's default hosts via a literal `inventoryGroups[component.Role]`
   lookup with no knowledge of `deploy_catalog.go`'s cosmetic `DefaultGroup` field, so this
   mismatch made the component **permanently unresolvable as any other component's dependency**
   (no possible wizard workaround) and broke its own empty-`target_group` default. `internal-endpoint`
   (which requires `freeipa-ca-trust` as a `planOnly` dependency) could not run *at all* until this
   was fixed. Fixed by correcting the contract's `role` to `all` — a one-line, well-contained fix
   confirmed safe against every other place `.Role` is consumed in the codebase (checked
   `ComponentsForRole`, `hostCardinality` validation, `sameHosts` dependency checks, the topology
   graph, and every regression test referencing this contract).
4. **Wazuh dashboard's docker-compose bundle hard-binds host port 443**, colliding with
   `reverse-proxy`/nginx on any host running both roles (this topology's own `nexus`). Confirmed
   live: nginx's `bind()` to `0.0.0.0:443`/`[::]:443` failed with "Address already in use";
   external connections to port 443 landed on Wazuh's own self-signed dashboard cert instead of
   nginx's `internal-endpoint` vhost for Grafana — the entire "reach Grafana via a clean internal
   HTTPS FQDN" feature was structurally broken whenever these two roles shared a host. Same *class*
   of issue as the already-documented `log-server`/`wazuh-manager` port-514 conflict this runbook
   fixed long ago, but for port 443. Fixed (user's explicit choice among 3 options) by remapping
   the dashboard off host port 443 in `wazuh-manager-apply.yml` (`8443:5601` via
   `ansible.builtin.replace` on the official compose file, after unpack, before compose-up). A
   stale nginx worker (already holding a failed-bind state from before the fix) needed one manual
   `systemctl restart nginx` to actually claim the now-free port 443 — expected for *this* session's
   pre-existing broken state, not a step future fresh deployments will ever need (a fresh topology
   never hits the conflict in the first place, since Wazuh claims 8443 from its very first start).

All four fixes are covered by regression tests (new: `TestRegression_FreeIPANFSClientConsumesRosterNFSClients`'s
existing assertions extended; `TestRegression_WazuhManagerDashboardOffPort443` new) and the full
suite (`go test ./...`, 1737+ cases) passes clean after each. `ansible-lint`/`--syntax-check` clean
on every modified playbook.

## Findings reported, not fixed (scope decisions — flagged for a future round, not acted on)

1. **The Plan B NFS mount itself (`client-vm` mounting `/sysops` from `nexus`) still cannot
   complete end-to-end in this topology**, even after every other fix above. Root cause, confirmed
   directly: `nexus.ipa.pilot.internal` has **no DNS record at all** in FreeIPA's own DNS —
   `dig @<freeipa-ip> nexus.ipa.pilot.internal A` returns `NXDOMAIN` from the authoritative server
   itself, independent of any client-side resolver configuration. Traced to
   `freeipa-client-apply.yml`'s `ipa-client-install` invocation, which deliberately passes
   `--no-dns-sshfp` with no `--enable-dns-updates` flag ("we don't manage DNS" — this project's own
   design choice to keep DNS management purely reconciler-driven via `freeipa-dns`'s explicit
   manifest, not automatic dynamic client registration). This is **not a Plan B defect** — the
   gate/targeting/verification mechanism itself is fully proven correct (confirmed: the gate
   correctly resolves `client-vm` via the roster hostgroup once the IPA automount map/key exists;
   the mount-verify tasks correctly detect and report the non-mounted state without crashing or
   false-passing). It is a separate, pre-existing architectural gap: any peer-to-peer service
   between this topology's own enrolled hosts that needs one host to resolve another by its FreeIPA
   FQDN has no path to do so today, since client hosts are never registered in FreeIPA's own DNS.
   Fixing this would mean either enabling dynamic DNS updates during enrollment, or requiring every
   such peer FQDN to be explicitly added to a `freeipa-dns` manifest zone — a real design decision,
   out of this round's authorized scope.
2. **`deploy_catalog.go`'s `Note` field for `freeipa-ca-trust`/`reverse-proxy`/`internal-endpoint`
   still describes each as "Phase-1 骨架:目前只有 placeholder task" (Phase-1 skeleton, placeholder
   only)** — stale documentation left over from before real Phase 2-7 implementation landed (all
   three now have substantial, real, already-independently-vm-tested logic, confirmed by reading
   each file in full). Cosmetic only (the `Note` text is informational, shown to the user before
   the target-group prompt) — does not affect behavior, but should be corrected in a future pass so
   operators don't distrust a feature that actually works.
