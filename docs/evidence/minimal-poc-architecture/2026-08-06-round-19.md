## Real findings this round

### 1. Playbook bug (fixed): `audit-log-forwarding-apply.yml`'s C20 fix only covered Debian family; RedHat family has the identical bug

Running the newly-added C20 regression check (full-directory `/etc/logrotate.d/` duplicate-path
scan) against this round's freshly-built `freeipa-server` (AlmaLinux 9) failed, while the same
check passed cleanly on `client-vm`/`nexus` (Ubuntu 24.04). Root cause: v1.3's remediation (Step
5a–5d in the apply playbook) gated the distro-rsyslog-policy fix to `ansible_os_family ==
"Debian"`. AlmaLinux's `rsyslog-logrotate` RPM package ships the identical `/etc/logrotate.d/`
filename (`rsyslog`) as a single shared block — just covering `cron`/`maillog`/`messages`/
`secure`/`spooler` instead of Debian's `mail.log`/`kern.log`/`auth.log`/`user.log`/`cron.log` — and
`audit_syslog_path` resolves to `/var/log/messages` on RedHat family, colliding with the module's
own `/etc/logrotate.d/syslog` exactly like the original 5-host Ubuntu incident. Confirmed live via
`vm-target exec` (`grep -rhoE '^/[^ {]+' /etc/logrotate.d/ | sort | uniq -c` showed
`/var/log/messages` twice; `rpm -qf /etc/logrotate.d/rsyslog` →
`rsyslog-logrotate-8.2510.0-2.el9.x86_64`). Fixed by dropping the `ansible_os_family == "Debian"`
condition from Step 5a-5d entirely — gating on `distro_rsyslog_logrotate.stat.exists` alone is
sufficient, since both families ship the identical filename/format. Re-verified on
`freeipa-server`: `--check --diff` preview showed the correct single-line diff (only
`/var/log/messages` removed, 4 other paths untouched); real apply `changed=1`; idempotent re-apply
`changed=0`; full spec re-run **60/60 PASS** across all 3 hosts. Bumped
`docs/verification/audit-log-forwarding.md` to v1.4, added
`docs/runbooks/audit-log-forwarding.md` §5.5.1, extended
`internal/spec/audit_log_forwarding_regression_test.go` to lock the fix. Full `go test ./...` —
1427 passed, 22 packages.

### 2. Authoring mistake this round (fixed, not a tool/playbook defect): HBAC target hostgroup missing `nexus`

This round's roster (authored fresh, not carried over) put only `client-vm.ipa.pilot.internal` in
the `poc-clients` hostgroup backing the `poc-ssh-access` HBAC rule, but
`scripts/minimal-poc-section4-spotcheck.sh` (and every prior round's own roster) targets **nexus**
for the live §4.1 checks. First spot-check run: 3/8 pass, all HBAC/sudo checks fail with a genuine
(and correct) HBAC denial (`journalctl -u ssh` on nexus: `pam_sss(sshd:account): Access denied for
user alice: 6 (Permission denied)`). Fixed by hand-editing the roster (tool-endorsed nested-YAML
exception) to add `nexus.ipa.pilot.internal` to `poc-clients`, then reconciling live.

### 3. Authoring mistake this round (fixed, not a tool/playbook defect, but reproduces a documented playbook limitation): reconcile for an unrelated change silently reset a personalized password

The hostgroup-fix reconcile above (an unrelated change) unexpectedly reset alice's
already-personalized password back to the roster's `initial` bootstrap value and re-armed her
forced-change flag — `krb5_child.log` on nexus showed `Password has expired` /
`Client's credentials have been revoked`. Root cause: alice's roster entry still had
`password.force_change: true` from the original onboarding, never flipped back after
personalizing. `playbooks/apply/freeipa-identity-apply.yml`'s own code comment (around "Passwords
are set unconditionally...") explicitly acknowledges this exact scenario ("someone forgetting to
flip it back after onboarding") as an unprotected gap — the `krbLastPwdChange`/
`krbPasswordExpiration` self-change-detection safety net only protects the `force_password: false`
case; `when: force_password OR needs_reset` means `force_password: true` alone forces the reset
regardless of self-change. Fixed by flipping `force_change: false` in the roster (one more
unavoidable `ipa passwd` reset happened on that reconcile, since `needs_reset` was already true
from the earlier stomp), then re-personalizing via `kinit` once more. Added a new §3.3
authoring-pitfall note and a new §6 gotcha row to the runbook.

### 4. Authoring mistake this round (fixed, not a tool/playbook defect): sudo rule missing NOPASSWD option

After fixing findings #2/#3, `sudo -n -l` still failed with `sudo: a password is required`. Traced
to `poc-sudo-rule.options: []` — never added `!authenticate` when authoring the roster.
Distinguished from the existing documented "stale SSSD sudo cache" gotcha by checking
`ipa sudorule-show poc-sudo-rule`, which showed the rule correctly attached but with no options at
all (a cache issue would show `!authenticate` already present). Fixed by setting `options:
["!authenticate"]`, reconciling, then refreshing the SSSD sudo cache on nexus per the existing
documented gotcha. Live-confirmed via `sudo -n -l` showing `(root) NOPASSWD: /usr/bin/systemctl
status ssh`. Added a new §6 gotcha row distinguishing this from the cache-staleness symptom.

### 5. Suspected implementation defect, reported not fixed: `pilot services status` reports a dead Harbor stack as healthy

`pilot vm-target topology up` failed with `services: Harbor is unreachable: ... connection
refused`, even though `pilot services status` had just reported `running=true`. `docker ps` showed
the Harbor containers `Exited (128)` ~28 hours earlier. Worked around via
`./pilot services down && ./pilot services up --profile dev-lite` (full recreate). Not root-caused
in Go source this round — out of the pre-authorized scope (the audit-log-forwarding fix); flagged
for a future round.

### 6. Documentation clarification, not a bug: `freeipa-client.md`/`freeipa-identity.md`/`freeipa-dns.md` are fixture-only specs

This is the first round to ever run `pilot verify` against these 3 of the 15 specs listed in the
runbook's §1 "aligned acceptance contracts" (no prior round's evidence shows it). All 3 specs'
Command/Expected columns are pinned to a fixed fixture (`pilotuser`/`fixture-group-a`/
`delete-fixture`/etc.) provisioned by each spec's own separate fixtures playbook, never by this
runbook's own roster/manifest — both `freeipa-identity.md` and `freeipa-dns.md` say so explicitly
in their own text. Results: `freeipa-client.md` 16/20 (C5/C8 fixture-bound), `freeipa-identity.md`
2/18, `freeipa-dns.md` 0/12 — all fixture-name mismatches, not tool/playbook errors. Added a
clarifying paragraph to runbook §1 so a future round doesn't mistake this for a regression.
