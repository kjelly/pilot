## Feature verification

**Fix #1 — FreeIPA DNS recursion wildcard:**

- Real apply log: `TASK [FreeIPA DNS — open allow-recursion/allow-query-cache to any client ...]` →
  `changed: [freeipa-server] => (item=allow-recursion)`, `(item=allow-query-cache)`.
- Live config on `freeipa-server` (`/etc/named/ipa-options-ext.conf`):
  ```
  allow-recursion { any; };
  allow-query-cache { any; };
  ```
  (directly below FreeIPA's own commented-out `trusted_network` example, confirming this is the
  documented customization point, not a hand-edit of `named.conf`).
- Real end-to-end resolution proof: `dig +short archive.ubuntu.com @192.168.122.2` run **from
  `client-vm`** returned real answers (`archive.ubuntu.com.cdn.cloudflare.net.` /
  `104.20.28.246` / `172.66.152.176`) — this is the exact failure mode (a `freeipa-dns-client` host
  unable to resolve a public domain via FreeIPA) that motivated the fix, now resolved.
- `pilot verify docs/verification/freeipa-server.md --host freeipa-server`: **PASS 20/20**, including
  `C20: pass, rc=0 matches expected 0`.
- Idempotency: a same-day single-component rerun of `freeipa-server-apply.yml` reported both
  `allow-recursion`/`allow-query-cache` items as `ok` (not `changed`) — `freeipa-server
  ok=26 changed=2 failed=0`, `✅ 套用完成`.

**Fix #2 — roster-autofill regression fix:**

- Real apply log, before preflight ever gets a chance to reject anything:
  ```
  ℹ️  freeipa_roster_file 未設定，自動帶入 /home/kjelly/.../demo/.vault/ipa-identity.yaml
  ```

## Findings for §6 gotchas (both self-inflicted this round, not product defects, but worth documenting)

1. `pilot vm-target topology up`'s cross-node "wire" step failed once with `Error: wire
   "freeipa-server": peer "nexus" has no IP yet; bring it up first`, even though all three VMs had
   genuinely started booting — an immediate identical retry succeeded once DHCP leases landed. The
   wire step appears to check peer IPs once rather than retrying under concurrent bring-up.
2. Recreating only `freeipa-server` via `pilot vm-target down --name freeipa-server` + `topology up`
   (e.g. to recover from an unrelated issue) invalidates every other already-enrolled host's CA
   trust, not just its IP (the existing §6.1 row about this only mentions the IP) — a fresh
   `ipa-server-install` mints a new root CA every time, so `nexus`/`client-vm` need
   `ipa-client-install --uninstall` + re-enrollment, not just an updated `ansible_host`.
