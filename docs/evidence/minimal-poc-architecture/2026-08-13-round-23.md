## The round's main finding: the runbook's roster-manager description was stale

No product defect was found. The significant finding is a documentation one, and it has a
compliance edge rather than being merely cosmetic.

§3.3 described `pilot edit`'s `roster` item as "append-only `👤 Users` / `👥 Groups` CRUD"
writing only `{name, state}`, and listed HBAC rules, sudo rules, hostgroups, group/user
membership, and a user's `password`/`ssh_keys` as things that "the edit menu still cannot
do" and must be hand-edited. **All of those have real wizard editors.** Verified against
current source and then exercised live this round:

- **Users** — per-field editors including masked `password.initial`,
  `password.force_change`, `password.preserve_existing`, and `ssh_keys.values`.
- **Groups** — `type`, `description`, `gid`, `membership.authoritative`, and
  `membership.users`/`membership.groups` as checklists.
- **Host access** — `Hostgroups` (incl. `membership.hosts` and nested
  `membership.hostgroups`), `HBAC rules` (add + edit of `subjects.groups`,
  `targets.hostgroups`, `services`), and an `hbac.disable_allow_all` toggle.
- **Sudo** — `Command groups` and `Sudo rules` (add + edit of `subjects.groups`,
  `allow.command_category`, `allow.command_groups`, `allow.commands`).

Why this matters beyond accuracy: the shared clean-room contract's Pilot-ownership rule is
that *everything the wizard will edit must go through it*. Following the old list therefore
put an operator in violation of the contract the same runbook mandates. §3.3's roster
bullet and its "cannot do" list are both rewritten, and the genuinely wizard-impossible
remainder is now enumerated precisely.

### What is genuinely still hand-edit — and two consequences worth knowing

1. `netgroups` — no screen at all.
2. `nfs.servers[].shares[]` / `nfs_clients` — no screen; the bootstrap writes `shares: []`.
3. **An HBAC rule's `subjects.users` and `targets.hostcat`.** The editor offers only
   access-group subjects and hostgroup targets, and `pushRosterHBACTargets` actively
   `delete`s `hostcat`. So the **`breakglass-admin-access` rule that
   `freeipa-identity-apply.yml` demands before it will disable `allow_all` cannot be
   authored through the wizard at all.** It must be hand-written *before* the
   `disable_allow_all` toggle is flipped. Round 23 sequenced it that way deliberately.
4. **A sudo rule's `options`.** `newRosterSudoRule` hard-codes `options: []` and no screen
   edits the field — a documented safe default. Consequence: `!authenticate`, which
   §4.1's `sudo -n` checks require, is *always* a hand edit on a wizard-created rule. §6's
   row treated this as an "authoring mistake"; it is reclassified.
5. A sudo rule's `deny`/`run_as`/`targets`, and any rule's `enabled` flag.
6. `freeipa.*` beyond `admin.{principal,password}`.
7. Deletion — the user `state` picker deliberately excludes `absent`; nothing deletes a
   group, hostgroup, HBAC rule, sudo rule or command group.

## Five further documentation defects, all corrected

1. **§2's vault key list was wrong in both directions (high).** It named
   `alertmanager_config` as required — `internal/inventory/vault.go:147` marks it
   `Optional: true` and the generator emits it commented-out — and omitted
   `node_exporter_basic_auth_password` (line 134, no Optional flag), which genuinely is
   required and must match `host-monitoring`'s copy or Prometheus's scrape is 401'd.
2. **§6.1's cwd-shadowing row named the wrong mechanism, and its diagnostic is actively
   misleading (high).** `Runner.Run` really does not set `cmd.Dir`, but for
   `ansible-playbook <playbook>` the `host_group_vars` plugin reads the inventory and
   playbook directories, not the cwd. A controlled probe with inventory, playbook and cwd
   in three separate directories, each holding a conflicting `group_vars/<group>.yml`,
   resolved the **inventory-adjacent** value. Ad-hoc `ansible` *does* use cwd as its
   basedir, so the row's prescribed `ansible -m debug -a "var=<key>"` reports a value the
   real deploy never uses. Round 23 hit exactly that false positive: round 22's isolated
   cwd had accumulated six verbatim copies of unfilled `*.example.yml`, `ansible -m debug`
   reported `thanos_s3_target_host: ""`, and the live host had every derived alias
   correctly mapped to nexus in `/etc/hosts` — so **round 22's site deploy used the real
   values and its PASS stands.** A different cwd sensitivity may still exist (vars-file
   paths reach `ansible-playbook` unresolved as `-e @<path>`), but that is not what the row
   described and was not re-tested.
3. **§6.1 carried a fixed defect as live for four rounds (medium).** The
   `identity_hbac_test_host` crash row was marked "reported not fixed (round 17)" with a
   mandatory roster workaround, yet the exact fix it proposed landed 2026-07-30 in
   `e5c56c4` — before round 18. Confirmed live by authoring this round's roster with **no**
   `freeipa.server` key, precisely the bootstrap-produced shape the row said would crash;
   the preview passed `failed=0`. Moved to §6.2.
4. **§3.5's reconcile prompt chain was undocumented (medium).** It differs from §3.4's
   site-wide chain in two ways. The `freeipa-server` in "select freeipa-identity,
   freeipa-server, sandbox" is a **text** prompt (`-e target_group=`, empty = the
   contract's default group) sitting between the component and stage menus — round 23's
   first scripted attempt expected the stage menu there and stalled, before any mutation.
   And there are **no** auto-detected `-e` confirms at all: §3.4's seven come from the
   site-wide `siteAutoHostVars()` loop, while the catalog path iterates only the selected
   component's own `AutoHostVars`, and `freeipa-identity` declares none.
5. **§3.3's `CHANGE-ME` check produces a false positive (low).** A correct, fully-filled
   vault still greps one hit: the generator writes optional keys commented-out but keeps
   their `CHANGE-ME-…` placeholder, so `ipa_dm_password` matches forever. The check must be
   scoped to uncommented lines.

### Two reproductions worth recording

- **The stale-SSSD-sudo-cache gotcha is not occasional — expect it every fresh run.** The
  spotcheck scored 6/8 with both alice-sudo rows failing `sudo: a password is required`,
  then 8/8 immediately after `sss_cache -E && systemctl restart sssd` on `nexus`, with no
  roster change in between. `ipa sudorule-show` already showed `!authenticate`, which is
  what distinguishes this from §6's NOPASSWD row. §4.1 now says so.
- **`-o StrictHostKeyChecking=accept-new` is not sufficient after a rebuild.** It accepts
  an *absent* key, not a *changed* one, so a stale `known_hosts` entry fails the login
  before PAM is ever reached — which then looks like a denial. The first denial-check cast
  failed this way and is preserved as a diagnostic. Durable home is the trec skill per
  AGENTS.md v1.15; the repo's own spotcheck script already uses
  `StrictHostKeyChecking=no` + `UserKnownHostsFile=/dev/null` + `ControlMaster=no`.
