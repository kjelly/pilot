## Real findings this round

### 1. Implementation defect (fixed 2026-07-26): `pilot deploy`'s hard gate requires `ipa_dm_password` despite it being marked `Optional`

`internal/inventory/vault.go`'s `ipa_dm_password` catalog entry (line ~42-45) is declared
`Optional: true`, and `GenerateVaultSkeleton` correctly writes it as a **commented-out** line in a
fresh vault skeleton for exactly that reason. `docs/verification/freeipa-server.md` independently
documents it as not required (falls back to `ipa_admin_password`). But
`ExpectedVaultKeysForRoles`/`checkVaultCompleteness` (`cmd/pilot/cmd/workspace_completeness.go`)
build their "expected key" list from `vaultSection.keyNames()`
(`internal/inventory/vault.go:23-29`), which returns every key in the section **without checking
`Optional`**. `pilot edit`'s own "🔍 檢查設定完整性" report is advisory-only, so it just shows the
same ❌ without blocking anything — but `pilot deploy`'s hard gate
(`cmd/pilot/cmd/deploy_completeness.go`) treats any non-empty violation list as fatal, so a real
deploy is unconditionally blocked:

```
Error: inventory 完整性檢查沒過(1 項)：
  - vault: .vault/main.yaml: ipa_dm_password 未設定
```

Reproduced live before any vault key beyond `ipa_admin_password` was even added; worked around at
the time by adding `ipa_dm_password` to `.vault/main.yaml` anyway (equal to `ipa_admin_password`).

**Fixed 2026-07-26, authorized by the user:** `vaultSection.keyNames()`
(`internal/inventory/vault.go`) now skips keys marked `Optional: true`, so
`ExpectedVaultKeysForRoles`/`checkVaultCompleteness` no longer demand a value for `ipa_dm_password`.
`GenerateVaultSkeleton` was already independent of `keyNames()` (it iterates `section.Keys`
directly and checks `Optional` itself to decide whether to comment a line out), so this change only
affects completeness checking, exactly the one production caller
(`cmd/pilot/cmd/workspace_completeness.go`'s `checkVaultCompleteness`, reached from both `pilot
edit`'s advisory report and `pilot deploy`'s hard gate) that ever consumed the list. Verification:
new regression test `TestExpectedVaultKeysForRoles_ExcludesOptionalKeys`
(`internal/inventory/vault_test.go`); full `go test ./...` (988 tests) passes; re-verified live
against the exact original repro — removed `ipa_dm_password` from this round's own
`tmp/pilot-verify-minimal-poc-r16/demo/.vault/main.yaml` and re-ran `pilot deploy` against the
still-running round-16 VMs, confirming the gate no longer fires
(`fix-verify/fix1-deploy-gate.cast`). The temporary wizard-driver workaround was removed and this
workspace's vault file was restored afterward to match what's actually deployed live.

### 2. Implementation defect (fixed 2026-07-26): a roster user with no `ssh_keys` field crashes the identity reconciler on ansible-core 2.19.x

`playbooks/apply/freeipa-identity-apply.yml`'s "Normalize canonical users for the compatibility
reconciler" task (~line 300) does:

```jinja
'ssh_keys': (item.ssh_keys | default({}))['values'] | default(none)
```

For a roster user with **no `ssh_keys` field at all** — exactly what `pilot edit`'s new roster
manager's `➕ 新增 User` produces (it writes only `{name, state: present}`) — `item.ssh_keys` is
undefined, `default({})` yields a genuinely empty dict, and `{}['values']` collides with the dict's
own `.values` method. Confirmed live: `pilot reconcile`'s preview failed with

```
Type 'method' is unsupported for variable storage.
<bound method _AnsibleLazyTemplateDict.values of {}>
```

against ansible-core 2.19.2 (this control node's installed version — `ansible [core 2.19.2]`).
Every prior round's roster populated `ssh_keys` for every user (copied from the committed example
roster), so this exact path was never exercised before the roster manager started producing bare
entries. Reproduced deterministically: adding `ssh_keys: {authoritative: true, values: []}` to
both `alice` and `bob` made the identical preview pass cleanly (`failed=0`), then a real apply
succeed (`changed=15`). No mutation occurred on the failing attempt (the crash is a template-render
error inside a `--check`-mode preview task).

**Fixed 2026-07-26, authorized by the user:** changed the offending expression to
`(item.ssh_keys | default({})).get('values', none)` — a real dict-method call, which Jinja compiles
as `getattr` + invoke, not the ambiguous item-then-attribute-fallback path a bracket subscript
takes. This exact `.get(...)`-on-a-defaulted-dict idiom was already in live use elsewhere in the
same file (`ipa_pwd_needs_reset | default({})).get(item.name, true)`, ~line 685), so this isn't a
novel pattern for this codebase. Verification: `ansible-playbook --syntax-check` passes;
re-verified live against the exact original repro — removed the `ssh_keys` blocks from `alice` and
`bob` in this round's own roster and re-ran `pilot reconcile`'s preview against the still-running
round-16 VMs, confirming it now completes cleanly (`✅ 預覽完成，沒有錯誤`, `failed=0`,
`fix-verify/fix2-reconcile-sshkeys.cast`) instead of crashing. The roster file was restored
afterward to match what's actually deployed live. `ssh_keys` is no longer a required field on any
roster user — add it only when a user actually has an SSH public key to authorize.

### 3. Own topology-authoring gap: `freeipa-server`'s declared VM memory was marginal for its own component minimum

`pilot deploy` aborted before any preview:

```
Error: delivery transaction failed: component "freeipa-server" host "freeipa-server" resources
cpu=2 ramMiB=3911 diskGiB=28 are below minimum cpu=2 ramMiB=4096 diskGiB=20
```

`deploy_facts.go` (commit `be48644`, 2026-07-24 — one day before this round) added real per-host
OS-fact gathering ahead of this exact check; before that commit the check always saw "facts
unavailable" and silently passed, so this is the first round in which it could ever fire for real.
AlmaLinux 9's actual usable RAM under this topology's KVM/virtio overhead landed ~185 MiB below the
nominal `memory: 4096` `vm-target`/topology-spec value — not a regression, just a marginal sizing
that a newly-real check correctly caught. Fixed by bumping
`docs/topologies/minimal-poc-topology.yaml`'s `freeipa-server` node to `memory: 4608` and
recreating just that one node (`pilot vm-target down --name freeipa-server` +
`pilot vm-target topology up` — the topology's own idempotent skip left `nexus`/`client-vm`
untouched). The recreated node received a **new DHCP-assigned IP** (`.5`, was `.4`) despite an
unchanged MAC address; `hosts.yml`'s `ansible_host` for `freeipa-server` was corrected via `pilot
edit` and `pilot inventory generate` re-run before redeploying. This is a scenario-authoring gap
(topology sizing), not a product defect.

### 4. Own roster-authoring mistake: sudo grant named the wrong systemd unit for the target OS

The roster's `poc-sudo-access` sudo rule granted `/usr/bin/systemctl status sshd`, matching
`scripts/minimal-poc-section4-spotcheck.sh`'s own stated default — but the live target
(`nexus`) is Ubuntu 24.04, where the real unit is `ssh.service`, not `sshd.service` (confirmed via
`systemctl status ssh` vs. `systemctl status sshd` on the live host; AlmaLinux/RHEL and
Debian/Ubuntu genuinely differ here). `sudo -n /usr/bin/systemctl status sshd` failed with `Unit
sshd.service could not be found` even though `sudo -n -l` correctly showed the grant attached.
Fixed by correcting the roster to `/usr/bin/systemctl status ssh` and re-running `pilot reconcile`
— a real, useful live exercise of the identity reconciler's **drift-correction** path (§4.4):
`changed=3 failed=0`, and the corrected command then worked. This is purely an authoring mistake
(picking a command that matches the verification script's stated default without checking it
against the actual target OS), not a tool or playbook defect.

### 5. Verification-script bug, fixed this round: Thanos `up` check silently reported empty on a real success

`scripts/minimal-poc-section4-spotcheck.sh`'s `4.2-thanos-up` check captures
`pilot vm-target exec ... -- curl ... 2>&1`, merging `pilot vm-target exec`'s own SSH host-key
warning ("Warning: Permanently added ... known_hosts") into the same stream as the real Thanos JSON
response. Depending on SSH/curl buffering, that warning line landed either before or after the
JSON on different runs; either way, a plain `json.load()`/`json.loads()` on the whole stream failed
(caught by the script's own broad `except Exception: pass`), leaving `value=''` even though the
script's own `raw:` diagnostic in the failure message showed a genuine `"value":[...,"1"]` result.
Fixed by parsing with `json.JSONDecoder().raw_decode(raw, raw.index("{"))`, which tolerates
trailing garbage the way `json.loads()` does not. Re-verified against both warning orderings
observed live. This is a script bug, not a `pilot`/Ansible defect — fixed directly in this round
(see the runbook's `AGENTS.md`-aligned rule that trec-driver/tooling issues are fixed at the
source, distinct from the two suspected `pilot`/playbook defects above, which were reported rather
than patched).

### 6. Trec-driver finding: `TOGGLE docker` is ambiguous on the role checklist

`TOGGLE docker` (and equally `SELECT docker`/`CHOOSE docker`) on the ~21-row role checklist errors
"ambiguous selectable label rows" — two *other* rows' description text contains the substring
"docker" ("需先過 docker", for `wazuh-manager` and `seaweedfs-s3`). `TOGGLE docker-apply.yml` (the
row's own unique suffix) resolves it. Documented in the `pilot-trec-verification` skill's §7
gotchas, not here — this is a trec-driver issue, not a runbook or product issue, per that skill's
own routing rule.

### 7. Skill correction: `pilot-trec-verification`'s `freeipa-identity` vars-file guidance was stale and actively wrong for the current canonical roster

The skill documented answering `n` to the `.vault/main.yaml` auto-detect prompt and redirecting the
wizard's vars-file prompt at the roster path instead — correct once (2026-07-17, v8), for a
roster shape that predates both the `freeipa_roster_file` host-var mechanism and the canonical
top-level-key gate. Against the current canonical roster (which structurally cannot carry a bare
top-level `ipa_admin_password` — see the runbook's own §2), that sequence now fails outright before
any ansible-playbook run:

```
Error: delivery transaction failed: component "freeipa-identity" requires input "ipa_admin_password"
```

Reproduced live on the first `pilot reconcile` attempt this round (no mutation — the Go-side
contract check runs before the preview). The runbook's own §3.5 already documented the correct `y`
answer; only the sibling `pilot-trec-verification` skill had drifted. Corrected in that skill this
round, with the historical context preserved so a future re-verification of a genuinely old
roster shape isn't misled by the correction either.

## Evidence integrity

10 casts were produced this round and kept as evidence; all 10 passed `mcp__trec__cast_verify`
(complete, exit 0, 0 secret-scan findings, safe to share, each with an expected `recording was
produced by a dirty trec build` warning — the locally installed `trec` binary itself is a
dirty/dev build, unrelated to the `pilot` candidate under test). **An 11th cast was produced,
leaked two secrets in plaintext, and was deleted rather than kept — `cast_verify` never ran on it,
so it did not pass a check, it was simply never checked before being caught by other means.**

An early group_vars-fill session (recorded to `03-edit-groupvars-vault.cast`) was, mid-session,
also used to start adding `.vault/main.yaml` keys without having declared `--secret-file` for
`grafana_admin_password` — the vault key-list screen renders every saved value in plaintext by
design (no per-field redaction hook, a limitation prior rounds' evidence already documents). That
session was closed and a corrected one (`03-edit-vault.cast`, with every secret declared via
`--secret-file` up front) was recorded in its place for the vault-fill step itself — but the
original file was not actually deleted at the time despite intending to, and the group_vars edits
earlier in that same recording (audit-log-forwarding/dashboard/prometheus/restic-backup/
thanos-query/wazuh-fim — all real, non-secret file writes) were never separately re-recorded. The
leak (both `grafana_admin_password` and `ipa_admin_password` in plaintext) was only discovered
during final review of this evidence, when a repo-wide grep across casts for known secret values
found 6 matches in that one file and 0 in every other kept cast. `03-edit-groupvars-vault.cast` and
its `.result.json` were deleted at that point. Both credentials are local to this disposable
sandbox topology and were never shared or published; they were not rotated (that would need a live
`ipa passwd admin` against the running FreeIPA server, re-running reconcile, and is left to the
user's judgment given this environment's disposable, local-only scope — see the runbook's own
teardown note). If this workspace or its evidence is ever kept beyond local disposable use, rotate
both before doing so.

Net effect on the checkpoint matrix above: the group_vars-fill step (audit-log-forwarding through
wazuh-fim) has **no surviving recording**, even though its file changes are real and were verified
by reading the saved files back at the time (see the checkpoint matrix's own PASS for that row —
downgrade the *recording* half of that claim; the *file-state* verification stands). No `trec mcp`
sessions were left open.
