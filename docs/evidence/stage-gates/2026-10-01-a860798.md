# Rollback and prerequisites under tag-scoped runs — 2026-10-01

Covers candidate `a860798` on top of `main` `04d262d`. `--tags` filters a block's rescue like any other task list. Eight apply playbooks had untagged rescues around row-tagged steps, so a failed `--tags <row>` run, including one from `pilot deploy`'s single-component tags field, did not roll back. In six of them, some row tags also always failed, or rendered wrong values, because a task read a register or fact from a task those tags do not select.

The candidate:
- tags every rescue task `always` in agent-controller, alertmanager, dashboard, detection-engine, pam-oidc-sshd, prometheus, restic-backup and thanos-query;
- makes the rollback material run under any tags. This covers pam-oidc-sshd Step 1 and agent-controller's and detection-engine's Steps 3–5 (previous db/binary stat, upgrade decision, db backup, binary snapshot). A new Step 3d creates the backup directory on an upgrade;
- reads the render registers in the container `restart:` expressions with `(x | default({})) is changed` (alertmanager, dashboard, prometheus, thanos-query). It also tags pam-oidc-sshd Step 4 `C2` and makes agent-controller's listen-address resolve `always`;
- adds `TestRegression_RescueRunsWheneverItsBlockDoes` and `TestRegression_TaggedTasksReadOnlyWhatTheirTagsSet`, each with a ratchet allowlist for the playbooks not fixed here.

No spec row changes.

## Ansible behavior (localhost, ansible-core 2.19.2)

A block with one `C3` task that fails, run with `--tags C3`:

| Rescue tags | Result |
|---|---|
| none | rescue skipped; rc=2, `failed=1 rescued=0` |
| rollback task `always`, final `fail` untagged | rollback runs, `fail` skipped; **rc=0**, `failed=0 rescued=1` |
| every task `always` | rollback and `fail` run; rc=2, `failed=1 rescued=1` |

The second row is why the lint requires every rescue task to be `always`.

## Full runs

- At the candidate, alertmanager, dashboard, prometheus, thanos-query, restic-backup, agent-controller and detection-engine: first run rc=0, second run rc=0 `changed=0`. After each injected-failure run, a full run restored the component with rc=0.
- `--check --diff` of each of the eight playbooks on a fresh host (the VM with Docker only, plus the host-monitoring textfile directory): identical rc and `changed` on both sides. pam-oidc-sshd fails on both, see below.
- pam-oidc-sshd was not run in full. It wires a PAM module into sshd on the VM's only access path. Its rollback was tested with a simulated earlier install, as above.

## Found, not fixed here

- Twelve more apply playbooks have rescues that `--tags` skips: audit-log-forwarding, dcgm-exporter, freeipa-nfs-server, freeipa-realm-replacement, freeipa-server, host-monitoring, log-server, log-shipping, pilot-access-target-policy, snmp-exporter, wazuh-fim, wazuh-manager. They are listed in `rescueTagGapAllowlist`.
- Fifteen apply playbooks have row-tagged tasks that read registers or facts their tags do not select. They are listed in `taggedPrerequisiteAllowlist`. Where such a task sits in one of the twelve blocks above, fixing its rescue makes the deterministic failure roll back, so the two fixes have to land together.
- pam-oidc-sshd `--check` on a fresh host fails on both revisions. Check mode skips the build, so Step 4a's source is missing. The rescue then tries to restore from a backup that check mode only simulated.

## Redaction

No vault was used; every secret input was a dummy value. The variables file, binaries, stub and run logs were per-run files outside the repository and were removed afterwards, along with the VM.
