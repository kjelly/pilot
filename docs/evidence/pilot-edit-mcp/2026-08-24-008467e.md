### 3.1 Secret-masking rendered-frame check

Session: `env CI=1 /tmp/pilot-evidence-build/pilot edit --dir
/tmp/pilot-evidence-build/ws-vault-secret --presentation`, 100×40 PTY, recorded to
`/tmp/pilot-evidence-build/casts/01-vault-secret.cast`.

Navigated (empty workspace, so the vault file picker only offered "input another path",
not an existing-file row): top menu → `.vault/` → `📍 輸入其他 vault 檔路徑` → accept
default path → confirm "not exist, create new plaintext vault file?" → vault editor →
`➕ 新增 key` → key name `evidence_secret` → secret-value screen. The value
`PTY-EVIDENCE-SENTINEL-7q2mZx9` (29 chars) was typed in two chunks with the screen
captured mid-entry and at completion:

```
capture point: sentinel partially typed (12 of 29 chars: "PTY-EVIDENCE")
┃ 值（多行請直接輸入 \n）
┃ > ************

capture point: sentinel fully typed (29 of 29 chars)
┃ 值（多行請直接輸入 \n）
┃ > *****************************
```

12 and 29 asterisks respectively — exactly the typed length, no plaintext at any point.
Grepping the literal sentinel string against these two saved frame files, and separately
against every rendered-output (`"o",`) line of the raw `.cast` file, both returned **0
matches** (independently re-run by me against the artifacts on disk, not just the
sub-agent's self-report). The string does appear inside the cast's `"i"` (input/keystroke
echo) events — that is `trec`'s own record of what it typed, not rendered terminal
output, and was excluded from the "rendered frame" claim by construction (only `"o",`
lines were checked for that claim).

After submitting, the vault editor screen showed the new row as
`evidence_secret = <已設定>` — the same non-secret placeholder `displayVaultValue()`
(`cmd/pilot/cmd/edit_tui_vault.go`) uses for any populated secret, confirmed by reading
that function: it only ever surfaces `CHANGE-ME` placeholders in the clear, and prints
`<已設定>`/`<未設定>` for everything else. `💾 存檔並離開` was selected, producing banner
`✅ 已存檔 .../.vault/main.yaml`; the session then quit cleanly via the top menu's `離開`
(`exit_code=0`).

**Real mutation, not a false negative** — the actual file on disk:

```
$ cat /tmp/pilot-evidence-build/ws-vault-secret/.vault/main.yaml
evidence_secret: "PTY-EVIDENCE-SENTINEL-7q2mZx9"
```

The sentinel is genuinely there in the real workspace file, confirming the masked field
really carried the value through to the save path rather than the screen simply
discarding it (which would also, misleadingly, show "0 leaks").

**Noted and resolved anomaly**: `mcp__trec__cast_verify` flagged this cast as
`safe_to_share:false` with 1 finding (`inline-secret-assignment`). Investigated directly
rather than dismissed: the only match is the rendered line `evidence_secret = <已設定>`,
which trips trec's generic `key = value` heuristic scanner regardless of `<已設定>` being
Pilot's deliberate non-secret placeholder. This is a limitation of trec's generic
scanner, not a Pilot secret leak — confirmed by the byte-level grep above (0 real
occurrences of the sentinel in any rendered frame) and by reading
`displayVaultValue`'s own documented intent. For contrast, the smoke-test cast in §3.2,
which never touches a vault screen, passed `cast_verify` with `findings_count:0,
safe_to_share:true`.

## 4. `go test` regression — reconciling the reported 58 failures (closes gap 4)

Run against the same `008467e` tree, in this session's sandbox:

```
$ go build ./...                              # clean
$ go vet ./...                                 # clean
$ CI=1 go test ./... -count=1 -v               # 24 packages ok, 1616 passed,
                                                # 1 skip, 0 failed, exit 0
$ CI=1 go test -race -count=1 ./...            # 24 packages ok, 0 failed, exit 0
```

The single skip (`TestVerifyDir_GlobStemAnchor`) is a pre-existing, environment-
conditional skip unrelated to the TUI migration.

This directly contradicts the previously reported "1843 passed, 58 failed, 1 skipped."
That run could not be reproduced here. Specifically checked as candidate root causes,
each independently verified rather than assumed:

- **CI=1 omission**: `TESTING.md` §1 states PTY-backed TUI tests "在互動 shell 下會誤判,
  一律 `CI=1`". Re-ran the router/`teatest` flow tests (`-run "TestEdit" ./cmd/pilot/cmd/`,
  121 passed) and the MCP diagnose tests (`-run "TestMCPDiagnose|Diagnose"`, 48 passed)
  **without** `CI=1` as well — both still passed cleanly in this sandbox, which itself
  has no attached interactive TTY (consistent with `TESTING.md`'s framing: the failure
  mode is specific to an *interactive* shell, which this tool's execution environment is
  not). This doesn't prove the original run's teatest timeout was caused by CI=1
  omission, but it is the one documented, project-specific trigger for exactly that
  symptom, and it did not reproduce here either way.
- **Sandbox resource limits** (sockets, `DEFAULT_LOCAL_TMP`, `ansible-vault` setup)
  suspected in the original report: directly checked in this environment —
  `ansible`/`ansible-playbook`/`ansible-vault` are installed and run (`ansible-vault
  [core 2.19.2]`), `/tmp` is writable, and a Unix domain socket bind/connect/close
  succeeded. None of the preconditions the original report blamed are actually
  unavailable here.
- **MCP diagnose error-code mismatches** (3 reported): re-ran the diagnose test file in
  isolation (`-run "TestMCPDiagnose|Diagnose" ./cmd/pilot/cmd/...`, 48/48 passed) — no
  mismatch reproduced.

Conclusion: on this tree, in this environment, full regression is clean and reproducible
across two independent invocations (with and without `-race`) plus two additional
targeted re-runs of the specific areas the earlier report flagged. The earlier 58-failure
run most likely reflects a different, more constrained execution environment (a stricter
sandbox, missing `ansible-vault`, no writable temp/socket path, or an interactive-TTY
context tripping the documented `CI=1` requirement) rather than a defect in this tree —
but since that environment isn't available to inspect directly, this is reported as the
most likely explanation, not a proven root cause. If the 58-failure environment recurs,
capture `go env`, `ansible-vault --version`, and whether a TTY is attached, alongside the
failing test names, so the two data points can be compared directly.
