## The defect in `92e6063`

`92e6063` moved the static-DHCP lock from the data dir to
`--vm-dir/.network.lock`. The CLI lets two runs use the same network with
different `--vm-dir` values. They then lock different files, and both can
pick the same free IP. On `main`, where the lock is next to the state json,
runs with the same data dir and different VM dirs did serialize, so
`92e6063` also regressed that case.

## The fix

- The lock is `/tmp/pilot-vmtarget-network-<network>.lock`. It is keyed on
  the network name only (the URI is always `qemu:///system`), so data dir and
  VM dir no longer matter. Network names outside `[A-Za-z0-9_.-]` become a
  hashed file name. The path is fixed `/tmp`, not `os.TempDir()`, because
  `TMPDIR` can differ between two pilots on one host.
- An existing lock file is opened read-only and without `O_CREATE`. flock
  does not need write access. `/tmp` is sticky, and with
  `fs.protected_regular` (2 on this host) an `O_CREATE` open of another
  user's file there fails with `EACCES`, even for root. `O_NOFOLLOW` refuses
  a symlink at the path. A new file is created `0644` despite the umask.

The first full run without `GOFLAGS` failed 31 tests in `cmd/pilot/cmd` and
`internal/agentcontroller`, all with `build pilot binary: … error obtaining
VCS status: exit status 128`. The cause is outside the repository: an empty
`/tmp/.git` directory on the test host. Go does not treat a worktree's `.git`
file as a VCS root, so it walked up to `/tmp/.git` and ran `git status` in
`/tmp`. No pilot code reads the VCS stamp. With `-buildvcs=false` the same
checkout passes.
