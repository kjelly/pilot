### SSH-key path on this candidate

Relative to the previously accepted inputs (`e42f50c`), the SSH-key tasks and the helper's SSH journal functions changed in one way only. `tagged` was added to the run-tag condition of the three SSH cache stage gates, so they now also run under `--tags tagged`.

- **Live SSH acceptance test** (`TestRegression_IdentitySSHCacheLiveSSH`, PASS, 71.6s), run against both clients before the identity fixtures were applied:
  1. A preview and an apply with the key present; new key-only SSH logins succeed on A and B.
  2. Revoke the key. Both clients deny it explicitly at public-key authentication, **0.19s** after the apply finished (contract: ≤10s).
  3. Identical revoke apply: zero named-user and zero global cache operations. Both clients still deny.
  4. Re-add the key; both clients allow it.
- **Deferred SSH pair**, run after the fixtures:
  1. Revoke with client B deferred. The apply fails as PARTIAL (exit 2) at the convergence gate. Only the provider and A are verified, B alone remains pending, and A denies the key at public-key authentication.
  2. Identical retry without deferral (exit 0) verifies only the B pair, and nothing remains pending. Both A and B deny the key at public-key authentication.
  3. Restoring the key (exit 0) verifies all three pairs, with nothing pending. The follow-up login probe was refused at the PAM account phase, not at the key. The canonical identity fixture applied for spec verification sets `hbac.disable_allow_all: true`, and the test roster grants no HBAC rule. This is the expected HBAC result, not a key-cache result.

The earlier [e42f50c record](2026-10-22-e42f50c-live.md) also covers the real SSSD timeout, an unreachable client, crashes before and after the IPA key mutation, A→failed B→A with a stale receipt, and the 20 historical scope-rejection cases. Those cases were **not repeated live** on this candidate. Their code differs from the tested inputs only in the gate condition described above. On this candidate they are re-covered by the real-Ansible orchestration suite.

## Failures and setup boundaries

- **First fix candidate** (`8f64b6e`, superseded): the same tagged, interrupted and skip-tags phases passed live. An independent review then found that the behavior test could pass on first-adoption refreshes alone, because it started each scenario without a journal. It also found that a change made with the refresh option off was never delivered later. Both were fixed in this candidate, and the earlier live phases were repeated from the restored baseline.
- On that first candidate, the live SSH test failed. The controller's OpenSSH 10.2 prints a post-quantum key-exchange warning to stderr, and the probe compared combined output with the user name. The probe now compares stdout for a successful login and stderr for a denial. This is a test-harness defect; production code is unaffected.

  - the first test roster named its group without the required `team-` prefix, and the production roster gate correctly rejected the dry-run.

## Secret handling and a pre-existing exposure

Rosters referenced the admin credential as a template, and it was never passed in argv.

The exact-value scan covered all 8 vault values in their raw and JSON-escaped forms, across 148 raw artifact files. It found the sandbox admin credential in the private JSON-callback transcripts.

The cause is pre-existing roster handling: it is present in the previously accepted `e42f50c` and on main, and is not touched by this change. It was reported to the maintainer separately.

The raw artifacts stayed in gitignored private directories with owner-only permissions and are deleted after this record. This record contains no raw output, and the scan found no secret in this record or its pointer edits.

Redaction categories: generated and vault credentials, private SSH keys, internal addresses, the realm, disposable host and user identifiers, private cache names and absolute operator paths. Component versions, counts, timings and hashes are retained.
