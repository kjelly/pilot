## 1. Binary-clean opaque transport through the real ForceCommand path — PASS

From `tx-ws` (which has no hosts entry for the target: `getent hosts tx-target…` → empty), as local user `wsuser`, with
`ProxyCommand ssh -T tx-gw.ipa.pilot.internal -- pilot-transport-v1 %h`:

```text
$ ssh tx-target.ipa.pilot.internal 'whoami; hostname -f; echo SPIKE-OK'
transportuser
tx-target.ipa.pilot.internal
SPIKE-OK
```

- The outer hop (gateway) and the inner hop (target) both authenticated with the same FreeIPA user SSH key (`ipa user-mod --sshpubkey`), via SSSD `AuthorizedKeysCommand /usr/bin/sss_ssh_authorizedkeys` on both hosts. The Phase 5 automation can therefore run without typing any password on the transport path.
- 64 MiB of `/dev/urandom` went up with `scp` and came back down with `sftp`, and all three `sha256sum` values matched (`207a098ea7b231cc…`). `rsync -a` of a small directory tree also worked.
- Gateway process tree during a live transport:

  ```text
  sshd: transportuser@notty
   \_ sh -c /usr/local/libexec/pilot-session
       \_ /usr/bin/pilot portal-session
  ```

  `pilot portal-session` has no child process. The `sh -c` layer is the login shell that sshd uses to run the ForceCommand; dash does not `exec` it away. So AG63 must assert "`pilot portal-session` has no child" and must **not** assert "no `sh` anywhere in the session".
- The prototype had to delete the wrapper's `[ -t 0 ] || exit 1` by hand on `tx-gw`, which confirms spec §7.3: the TTY check must move into Go.
- The prototype's error path printed cobra's full usage block to stderr before `pilot-transport: access denied`, which confirms F18 (`SilenceUsage: true` is needed).

## 2. Gateway service principal can read host SSH keys — PASS

On `tx-gw` I ran `kinit -kt /etc/pilot/pilot-access-gateway.keytab pilot-access-gateway/tx-gw…` and then `ipa -vv host-show tx-target… --all`. The JSON-RPC response was made with `principal: pilot-access-gateway/tx-gw.ipa.pilot.internal@IPA.PILOT.INTERNAL`, and it returns `ipasshpubkey` as **plain strings** of the form `"<type> <base64> <comment>"`, not `{"__base64__": …}`. There were three keys: `ssh-ed25519`, `ssh-rsa`, `ecdsa-sha2-nistp256`. No extra FreeIPA permission is needed. The full response was saved verbatim as `internal/freeipaaccess/testdata/host_show_ipasshpubkey.json` (public host keys and test-VM names only).

(Contrast: `ipa user-show --all --raw` prints `ipaSshPubKey` base64-encoded. The identity fixture therefore compares against the non-raw `SSH public key:` line.)

## 3. Target sshd policy on Ubuntu 24.04 (OpenSSH 9.6p1) — PASS

Candidate drop-in `/etc/ssh/sshd_config.d/06-pilot-access-target-policy.conf` with `Match Address 192.168.122.4` (the gateway):

| Key (`sshd -T -C user=root,host=pilot-gateway,addr=<gw>`) | strict | remote-dev | `addr=192.0.2.1` and global |
|---|---|---|---|
| `allowtcpforwarding` | `no` | `local` | `yes` |
| `allowstreamlocalforwarding` | `no` | `no` | `yes` |
| `permitopen` | `none` | `localhost:* 127.0.0.1:* [::1]:*` | `any` |
| `permitlisten` | `none` | `none` | `any` |
| `gatewayports` | `no` | `no` | `no` |
| `allowagentforwarding` | `no` | `no` | `yes` |
| `x11forwarding` | `no` | `no` | `yes` |
| `permittunnel` | `no` | `no` | `no` |

- `sshd -t -f <drop-in>` → rc=0 for both profiles, so it works as the `copy` module's `validate`.
- Global `sshd -T` outside the 8 keys, and the complete `addr=192.0.2.1` output, were byte-identical before and after installing the drop-in. The Match block is scoped to its include file and does not leak into later settings.

On `tx-ws` (OpenSSH 9.6p1), with `UserKnownHostsFile /dev/null`, `GlobalKnownHostsFile /dev/null`, `StrictHostKeyChecking yes`, `UpdateHostKeys no`, `CheckHostIP no`, and `KnownHostsCommand <cmd> %h` combined with the transport ProxyCommand:

This confirms spec §12.4: that directive stays global (its default is already `no`).

## Findings outside the transport feature (both found while standing up this topology)

1. **apt stale metadata** — fixed and committed separately as `ad6d552` (`fix(apt)`, see `docs/verification/apt-repository-tolerance.md` T8). `freeipa-client` had a cached Candidate whose dependency `.deb`s already returned 404 from the mirror, and the shared apt task never refreshed.
2. **Portal group check uses the SSSD group member list** — `internal/identity.IsMemberOfGroup` reads `getent group role-pilot-portal-user`. SSSD had cached that group (with no members) at 08:34:56, with the entry valid until 10:04:56. The playbook's automember rebuild added `transportuser` after that, so the gateway API answered `{"error":"unauthorized"}` even though `id transportuser` already showed the group. `sss_cache -g role-pilot-portal-user` fixed it immediately. Removals have the same delay in the other direction: up to the cache lifetime. Reported to the user for a separate fix decision; the Phase 0 run worked around it with `sss_cache`.
