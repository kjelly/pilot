# ForceCommand preconditions under the drop-in's own tags (gateway and Directory) — candidate `458f123` (2026-10-03)

Scope: found while scanning PR #19 for checks with fewer tags than the write they protect. `pilot-access-gateway-apply.yml` Step 19 and `pilot-access-directory-apply.yml` Step 18 install an sshd ForceCommand drop-in that sends every portal user into a wrapper. The checks it depends on carried only the service tags:
- the health probe (gateway and Directory Step 17);
- the gateway's `pilot-target-<scope>` check (Steps 13 and 18);
- the portal-user group lookup.

So did `sshd -t` and the reload. `--tags AG43` (gateway) or `--tags AD18` (Directory) therefore wrote the drop-in with none of these checks, and never validated or loaded it.

The candidate adds "ForceCommand gate" tasks before the drop-in, under its own tags. They check that:
- the wrapper and `/usr/bin/pilot` are root-owned executables that group and others cannot write;
- the service answers `/v1/health` with `status: ok`. On the gateway this includes `target_scope`, i.e. `pilot-target-<scope>` resolves through the gateway's own credential, Step 18's check;
- the portal-user group resolves.

`sshd -t` and the reload carry the row tag too. The checks run only when installing, so disabling ForceCommand still removes the drop-in whatever the service's state.

## Regression tests

`internal/spec/forcecommand_gate_regression_test.go`:
- `TestRegression_ForceCommandInstallFollowsItsChecks`: every ForceCommand gate task runs before the drop-in, carries every tag of its install task and depends on the install variable; `sshd -t` and the reload carry the install's tags.
- `TestRegression_ForceCommandInstallIsCheckedUnderItsRowTag` runs both playbooks' ForceCommand tasks on localhost under the row tag (`AG43`, `AD18`) and the group tag (`AG_forcecommand`, `AD_forcecommand`).
  - The harness points the paths into a temporary directory and stubs `curl`, `getent` and `sshd`. The systemd reload is a debug observer, and the owner check expects the test's user.
  - Cases: a healthy host gets the drop-in validated and loaded. A service that is down or degraded (`target_scope: missing`), a missing or group-writable wrapper, and an unresolved group are each refused with nothing written.
- `TestRegression_ForceCommandRollbackIsNeverBlocked`: with the service down, the wrapper gone and the group unresolved, disabling ForceCommand still removes the drop-in, and no gate runs.
