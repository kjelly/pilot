## The race and its fix (`63f4cdc`)

`IngestEvents` checked `EndedAt` before opening its transaction, and
`FinishSessionResult` read the session and the stored seqs before an
unconditional `UPDATE`. Now every write transaction starts with `BEGIN
IMMEDIATE` (`_txlock=immediate`, as `internal/outbound` already does); start,
ingest and finish read the session inside their own write transaction; finish
updates only `WHERE ended_at=''` and requires one affected row; `Replay` reads
the summary and the events in one read transaction.

| Check | Before the fix | After the fix |
|---|---|---|
| `TestStoreConcurrentFinishAndIngestStayConsistent` (200 rounds of `IngestEvents(seq=1)` against `FinishSession(complete=true, last_seq=0)`, real SQLite) | FAIL: 1 round both succeeded (the finished session had event 1 above `last_seq` 0 and replayed `Complete=true`); 199 rounds ingest failed `SQLITE_BUSY` (the deferred transaction's read-to-write upgrade). A 500-round probe: 17 both succeeded, 483 `SQLITE_BUSY` | PASS 5 × 200 rounds: ingest won 70–91 (finish then `ErrLastSeqTooLow`), finish won the rest (ingest then `ErrSessionFinished`); no violation |
| `TestStoreConcurrentIdenticalStartsAreIdempotent` (two identical `StartSession` retries at once) | FAIL in the first round: `UNIQUE constraint failed: sessions.session_id` instead of the retry no-op | PASS 200 rounds |
| Live, over the store's TLS ingest API on a real `pilot-session-store` (transport topology below), 200 rounds of `events(seq=1)` against `finish(complete=true, last_seq=0)` with tokens signed by the run's signing key | binary built from `2b65e31` (the branch before the fix), swapped in temporarily: **23** rounds both 200, 59 rounds events 500, 115 events 409 / finish 200, 3 events 200 / finish 400. The auditor's list then held exactly 23 sessions with `complete true`, `event_count 1`, `last_seq 0` | candidate binary: 184 rounds events 409 (`session_finished`) / finish 200, 16 rounds events 200 / finish 400 (`last_seq below a stored event seq`); none both 200, no 500 |

After the negative control the candidate binary was put back (sha256 checked),
the service restarted, and a store re-apply was `changed=0`; store verify 27/27
and gateway verify 32/32 afterwards.
