# ForceCommand drop-in validated and put back on failure; `--tags AG43`/`AD18` also remove it (gateway and Directory) — candidate `cbab54a` (2026-10-12)

Scope: the PR #38 review's open items, on top of `9b851f6` (`2026-10-12-9b851f6.md`):
- If `sshd -t` failed, the new drop-in stayed on disk. The next run found it unchanged and skipped `sshd -t` and the reload, so it passed while sshd ran without the drop-in. sshd's next restart would load a configuration nothing had validated. Removing the drop-in had the same gap.
- The removal carried only `AG_forcecommand`/`AD_forcecommand`, so `--tags AG43`/`AD18` with the install variable `false` did nothing.
- The gateway's ForceCommand health gate checks the running gateway. This is unchanged: `--tags AG43` neither renders the config nor restarts the gateway, and the running gateway is what portal users reach. The spec now says so.

The change, in both playbooks:
- The install and the removal each run as a block: write the drop-in with `validate: /usr/sbin/sshd -t -f %s` (or remove it), run `sshd -t` on the whole configuration, then reload.
- The rescue puts the drop-in back the way the run found it, from a stat/slurp snapshot taken just before. It removes a file the run created. Then it fails the run. sshd was not reloaded, so the file on disk again matches what sshd runs, and the next run retries.
- The removal block carries `AG43`/`AD18`.
- New lint `TestRegression_SshdConfigWritesAreValidatedAndReverted`.

## Regression tests

`internal/spec/forcecommand_gate_regression_test.go` runs both playbooks' ForceCommand section on localhost, from the first gate to the rollback. The helpers now recurse into blocks and rescues, and the copy's `validate` runs a stand-in command. New and changed tests:
- `TestRegression_ForceCommandInstallFollowsItsChecks` also requires the three removal tasks to carry the install's tags (`AG43`/`AD18`).
- `TestRegression_ForceCommandRollbackIsNeverBlocked` now runs under the row tag as well as the group tag, and requires the reload.
- `TestRegression_ForceCommandFailedSshdCheckLeavesNoDropin` (new) has four cases under the row tag and the group tag:
  - `sshd -t` fails with no drop-in before;
  - `sshd -t` fails with a previous drop-in;
  - the drop-in fails its own validation;
  - `sshd -t` fails after removing the drop-in.

  In each case the run must fail with no reload, and leave the drop-in as it found it.
- `TestRegression_ForceCommandRetriesAfterAFailedSshdCheck` (new): after a failed `sshd -t`, the next run validates and reloads.

`internal/spec/sshd_config_write_regression_test.go` (new) lints `playbooks/apply` and `playbooks/decommission`. Every write or removal of `/etc/ssh/sshd_config` or `/etc/ssh/sshd_config.d/*.conf` must:
- have `validate` with `sshd -t -f %s`, when it writes content;
- sit in a block with a rescue;
- be followed by a whole-configuration `sshd -t` before any systemd/service task.

Writes inside a rescue are exempt. `TestSshdConfigWrites` holds 7 unit cases.

### Same class elsewhere, allowlisted

A scan of `playbooks/**` for sshd configuration writes found three more with the same gap. Each needs its own vm-target run to fix, so the lint lists them in `sshdConfigWriteAllowlist`. It fails once one is fixed.
- `freeipa-client-apply.yml` writes `05-freeipa-client-password-auth.conf` without `validate`, outside a block with a rescue, then **restarts** sshd without `sshd -t`. If another file in `sshd_config.d` is broken, the restart fails and sshd stays down.
- `freeipa-client-decommission.yml` removes the same file and restarts sshd without `sshd -t`.
- `pilot-access-target-policy-apply.yml`'s absent path removes its drop-in outside a rescue, and reloads only when the removal changed something. The policy left loaded is the restrictive one, and the host has already left `pilot-transport-ready`.

Test fixtures under `playbooks/test` are out of the lint's scope.
