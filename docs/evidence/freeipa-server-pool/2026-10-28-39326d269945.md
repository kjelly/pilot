as included from `dns-apply.yml` and `freeipa-client-apply.yml` by `playbooks/site.yml`.

- Candidate: `39326d269945c1da744b5b58b2c6ef1da6ea8ff1`.
- Tree: `42b43d6926432d847559323c8bc12bcaa2b2b4f7`; clean worktree, no tracked

- Control (base, untouched): `ff32bf63c40109b72f4b134cbf83889c7f881ab4`,

- Tooling: ansible-core 2.19.2; `pilot` binary built from the candidate.

## The bug and the target layout

Before the fix the task accumulated `freeipa_server_pool_replicas` across includes.
`site.yml` includes it from `dns-apply.yml` (`hosts: dns`) and then from
`freeipa-client-apply.yml` (`hosts: freeipa-client`), so a host in both groups, with a
`freeipa-server-replica` in inventory, listed every replica twice and failed the
duplicate-FQDN gate. No existing committed topology has this layout, so a throwaway
three-node vm-target topology (not committed) was used. Inventory facts were read from
`pilot vm-target topology inventory` and `ansible-inventory --graph` before any run:

| Node | Image | Groups |
|---|---|---|
| ipa node | almalinux-9, 4608 MiB, 2 vCPU, 30 GiB | `freeipa-server` |
| replica node | almalinux-9, 3072 MiB, 2 vCPU, 30 GiB | `freeipa-server-replica` |
| client node | ubuntu-24.04, 2048 MiB, 2 vCPU, 15 GiB | `dns` and `freeipa-client` |

SSH user root, generated vm-target inventory, `services: local`. Base image SHA-256:
almalinux-9 golden `b780998adca7c69ff6dbd41a05b51769ef6ab6708a7defbd286195186fbcc8ac`,
ubuntu-24.04 golden `bfab799e2c50a83f77c607e50290646c07628a67ed73fe90c28658a28b0a5394`.
The replica node is inventory-only: `site.yml` has no import for
`freeipa-server-replica`, so nothing installs FreeIPA on it. Every run used genuinely
fresh VMs.

It is not caused by this fix.

## What was not verified

- `freeipa-client.md` C5/C8 passing (needs the fixtures playbook first), and any
  `dns.md` verification (its inputs were not supplied): the chain's L5 for the client
  and dns specs is therefore not green, and L6 was run with only the server spec
  verified.
- A real replica install (the topology is inventory-only for the replica node) and
  real multi-replica HA behaviour of the client.
- Full `go test ./...`; this record covers the vm-target run only. The Go regression
  tests of the candidate are not part of this evidence.
