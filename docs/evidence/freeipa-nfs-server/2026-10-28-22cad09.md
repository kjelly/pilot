## Vault rotation through `pilot edit --actions`

**Workspace.** A scratch pilot workspace; the real vault directory was not used:

- `.vault/main.yaml` is a 0600 copy of the sandbox vault: plaintext, eight top-level scalar keys, 55 comment
  lines and 9 blank lines.
- `.vault/` also holds a 0600 copy of the match roster under a non-default name.
- `hosts.yml` lists the two hosts. `p148f-nfs` sets `freeipa_roster_file` to that roster's absolute path, so
  the sync had to find it through the reference; the default `.vault/ipa-identity.yaml` did not exist.
- `pilot` ran with a scratch `--data-dir`.

**Scenario.**

```json
{"version": 1, "steps": [
  {"action": "set_vault_value", "file": "main.yaml", "key": "ipa_admin_password", "value_env": "<env var>"},
  {"action": "save_vault", "file": "main.yaml"}]}
```

It ran as `pilot edit --dir <workspace> --actions <scenario> --data-dir <scratch>`. Each new password was
30 characters, generated by a script and never printed. It started with `0` and contained ` #`, `: `, `"` and
`'`, but no braces, Jinja delimiters, backslash or newline. It reached `pilot` only through the environment.

### (i) Rotation

`pilot edit --actions` exited rc=0, with nothing on stdout and no `warning:` lines on stderr. The files
afterwards, compared without printing any value:

- **Vault:** `ipa_admin_password` equals the generated password. The other seven keys keep their values, and
  all 55 comment lines are kept, unchanged and in order. Seven of the file's nine blank lines were dropped;
  this is the vault writer's existing yaml.v3 behaviour.
- **Roster:** `freeipa.admin.password` equals the generated password and the vault's value. Exactly one line
  of 187 changed, written as a double-quoted scalar, and the roster is YAML-identical apart from that value.
- **Other files:** `hosts.yml` is byte-identical. All three files stay 0600. The roster's two lock sidecars
  appeared beside it.

> step 2 (save_vault): `<workspace>`/.vault/main.yaml was not saved, so that it keeps matching its rosters: roster .vault/p148f-roster.yaml was not written: another pilot process holds its lock: inventory: already locked by another process

Afterwards, the sha256 of `.vault/main.yaml`, the roster and `hosts.yml` were byte-identical to before the
run, and the vault still held the password from (i). `.vault/` held exactly the same four names as before, the
two files and their lock sidecars, with no temp files.

### (iii) Hard-linked roster

A fresh scratch workspace. `.vault/ipa-identity.yaml` and `.vault/alias.yaml` were two names of one inode
(`ln`, not `ln -s`; link count 2, mode 0600), and `hosts.yml` set `freeipa_roster_file` to the **alias** name.
`.vault/main.yaml` was a separate 0600 copy of the sandbox vault.

1. **Busy.** Another process held an exclusive `flock` on the roster file itself, through the name
   `ipa-identity.yaml`; a probe through the other name, `alias.yaml`, confirmed it was held. A rotation exited
   **rc=1**, with an empty stdout and this stderr, workspace directory replaced:

   > step 2 (save_vault): `<workspace>`/.vault/main.yaml was not saved, so that it keeps matching its rosters: roster .vault/ipa-identity.yaml was not written: another pilot process holds its lock: inventory: already locked by another process

   The vault, the roster (both names) and `hosts.yml` were byte-identical to before. The refused attempt left
   only the roster's two lock sidecars (`ipa-identity.yaml.pilot-migrate.lock` and `.pilot-remove.lock`) in
   `.vault/`; there were no temp files.
2. **Released.** After the holder was killed, a probe confirmed the lock was free, and the same rotation exited
   **rc=0** with empty stdout and stderr. The shared inode holds the new password through both names: the two
   names are byte-identical, `freeipa.admin.password` equals the generated password and the vault's value, the
   inode number is unchanged and the link count is still 2. Exactly one roster line of 187 changed. The vault
   kept its other seven keys and all 55 comment lines. `hosts.yml` is byte-identical, and all files stay 0600.

The rollback journal was not triggered: no step failed after a roster write, so its undo path was not exercised
