## How unbound treats the allow-all spellings

One Ubuntu 24.04.4 VM, `apt-get install unbound` (1.19.2), one `access-control:` drop-in per case, then `unbound-checkconf`, a restart and `unbound-control get_option access-control`:

| Entries | `unbound-checkconf` | `get_option` prints |
|---|---|---|
| `0.0.0.0/0 allow` | rc=0 | `0.0.0.0/0 allow` |
| `1.2.3.4/0 allow` | rc=0 | `1.2.3.4/0 allow` |
| `::0/0 allow` | rc=0 | `::0/0 allow` |
| `::/0 allow` | rc=0 | `::/0 allow` |
| `0.0.0.0/1 allow`, `128.0.0.0/1 allow` | rc=0 | both, in reverse config order |
| `0.0.0.0/00 allow` | rc=1, "cannot parse netblock: '0.0.0.0/00'" | (unbound does not start) |
| `10.0.0.0/08 allow`, `10.1.2.3/8 allow` | rc=0 | as written |
| `0.0.0.0/0 allow_snoop` | rc=0 | `0.0.0.0/0 allow_snoop` |

unbound keeps the spelling it was given, so a string match on its output cannot detect an allow-all ACL. `0.0.0.0/00`, the example in the review, is rejected by unbound itself here (and by unbound 1.24.2 on the workstation), so G7 would have rolled it back; `1.2.3.4/0`, `::0/0` and the two halves are accepted. The `get_option` outputs are the fixtures of `TestRegression_DNSC5RejectsEquivalentAllowAll`.
