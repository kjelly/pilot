This is a narrow target run, not the L1–L6 chain: the change touches no playbook,
spec or contract. It exercises the teardown-ownership decisions of
`pilot vm-target topology up --fresh` against real libvirt, in the places where
the hermetic shim tests only prove pilot's own decisions (state file and `virsh`
call log), not libvirt-side effects.

## What was compared

Before the first scenario and after every scenario, one snapshot of the host:
pilot's state file (names and statuses), `virsh list --all` and the VM
directories. A scenario "leaves no residue" when the snapshot equals the
baseline and no snapshot contains the string `pr209smoke`. The network's static
DHCP reservations carry only a MAC and an IP, no name, so they were compared
separately: two entries (the foreign VMs') before, four while B's two nodes were
up, two after B's `down` and two after A.

## Not exercised live

- The wiring-failure teardown and the race in which another process claims a
  declared name between the absent check and `Manager.Up` cannot be provoked on
  a shared host without touching a foreign VM. They are covered only by the
  hermetic tests (`TestTopologyUpFresh*`, `TestTopologyTestEphemeral*` in
  `cmd/pilot/cmd`), whose oracle is pilot's state file plus a fake `virsh` log.
  Each was shown to fail when its fix is reverted.
- `make poc-checkmode-test` was not run end to end (it needs the three-VM
  minimal-poc topology and its vault). The script's one change is
  `topology up --fresh` in place of `topology up`, with the EXIT trap installed
  after it; the order is locked by `TestTopologyCheckmodeScriptInstallsItsTrapOnlyAfterUpFresh`.
- A SIGINT or SIGTERM during `up --fresh` is not handled (the CLI has no signal
  handling and uses `context.Background()`); half-created VMs are left, and the
  next run refuses their names. This is the behavior of plain `up` as well.

## Redaction

MAC addresses, host-local paths and the names of the other sessions' VMs are
omitted. No secret was read by any command.
