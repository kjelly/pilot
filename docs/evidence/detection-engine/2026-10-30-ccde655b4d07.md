# Detection Engine install-block backup selection and rescue availability (PR #190, refs #189) — candidate `ccde655b4d07`

Scope: `playbooks/apply/detection-engine-apply.yml` took its "pre-upgrade" backup (Steps 3–5, `always`-tagged) on every run, including runs that never reach Step 6 (the binary replacement), so a `--tags docker` run kept changing the target (#189). Its rescue also restarted the service into whatever configuration the failed run had written and did not put back the unit, `config.yaml`, feature profile or `provider.env`. The candidate (a) gives Steps 3–5 Step 6's own tag, so backup and upgrade detection run exactly when Step 6 does; (b) reads the service's original state read-only in Step 0 (outside the block, so an unreadable state is a refusal before any change, not a rescue); (c) snapshots the four rewritten files in memory (Step 0b–0d) and restores them, byte/mode/numeric owner/group, before the rescue restarts the service. This record shows those behaviours on a native systemd service, side by side with the base on the same snapshot. Invariants:

| ID | Invariant |
|---|---|
| I1 | Steps 3–5 run iff Step 6 runs; a run that does not select Step 6 changes nothing (second run `changed=0`) |
| I2 | After an upgrade, `.prev` is the old binary and `pre-upgrade.db` passes `db check` |
| I3 | After a failure inside the install block the service is as Step 0 found it (active/enabled), `NRestarts` is stable, the pre-run binary is back if it was upgraded, and unit/config/feature profile/`provider.env` are back byte for byte with mode and owner; `NeedDaemonReload=no` |
| I4 | An unreadable service state is a refusal: no stop/disable/restart, `MainPID` and `ExecMainStartTimestamp` unchanged |
| I5 | A first install (no unit) is accepted |
| I6 | No synthetic secret (nor its base64) in any output |
| I7 | Normal chain: L1, L3, L4, L5 (12/12), L6 `changed=0` |

## Deviations from the written plan, and what they affect

- The first launch of the HEAD arms ran the two `--tags docker` arms and Fa without a fact cache. Tag-scoped runs do not run the implicit "Gathering Facts" task, and the driver wipes the per-run fact cache after each snapshot revert, so host-monitoring's OS gate failed ("`ansible_distribution` is undefined") before detection-engine's play was reached. Those three outputs were set aside as invalid and the arms were rerun after a read-only `ansible -m setup` re-created the cache (the repo's own `ansible.cfg` has `gathering=smart` and a jsonfile cache, so operators normally have one). The same step ran before every tag-scoped control arm. Failure was in the harness, not in the candidate. U0, U0 second run and the verify run were unaffected (a full run gathers facts) and were not rerun.
- The first launch of the arms also died between arms (its parent was reaped); the remaining arms were started again from the same snapshot with the driver detached.
- The plan's unit-test step was replaced by the local checks above, run on the candidate commit in the same tree.
- The plan expected no difference between the PR base and the control over the execution list; four FreeIPA-only task files under `playbooks/apply/tasks/` differ. detection-engine and host-monitoring do not include them.
- The recorded `go version` line was first written from the wrong directory (it showed the 1.24 toolchain on PATH); the binaries were built, and the tools line corrected, with go1.26.8.
- The first golangci-lint run reported 70 issues from stale entries in a shared lint cache that point at other sessions' checkouts; with an isolated cache the same command reports 0.
